- 日期：2026-10-14

## 一句话回答

| 问题 | 回答 |
| --- | --- |
| 1 标签：大模型加人工，1 万对起步 | 方向对。但比"对数"更值钱的有两样：判官的准确率，以及 query 的个数。1 万对要先定好怎么拆给 train、dev、holdout，各自能测多准，见第一节 |
| 2 数据定了以后，普通调参和 agent 调参有区别吗 | 基本没区别，而且 agent 更差。数值参数交给优化器，agent 不碰数值。Karpathy 那边的毛病正出在这里 |
| 3 数据要覆盖各分数段吗 | 要覆盖，但评估集和训练集抽法不同。另外，"分数分布不偏"靠偏序标签管不住，要靠档位标签和无标签样本 |
| 4 提新特征时 agent 能做得更好吗 | 是的，这才是 agent 该干的活。前提是给它足够的原始字段，并且用 train 上的交叉验证筛选，不去消耗 dev |
| 5 内网只有 OpenAI 格式接口、可能没有搜索，够用吗 | 够用。这个循环不需要联网搜索，需要的工具也很少。最大的变量是模型本身的代码与工具调用能力，要先做一轮资格测试，见第五节 |

## 一、标签：1 万对怎么拆、判官准不准比多不多更重要

### 1.1 判官的准确率直接打折扣

设判官在非"相当"对上与真实答案一致的概率为 q，判错是随机的。那么任何改动在标签上**观测到的提升 = (2q − 1) × 真实提升**。噪声的标准误基本不变，所以要测出同样大的真实提升，需要的数据量要乘上 1 / (2q − 1)²：

| 判官准确率 q | 观测提升打几折 | 要测出同样的提升，数据量需要乘以 |
| --- | --- | --- |
| 0.80 | 0.60 | 2.8 |
| 0.85 | 0.70 | 2.0 |
| 0.90 | 0.80 | 1.6 |
| 0.95 | 0.90 | 1.2 |

**判官从 85% 提到 90%，相当于白送了约 30% 的数据量。** 所以"确定这批数据的准确性"这一步不是走个形式，它直接决定 1 万对能当几千对用。提高 q 的办法：

- 两种顺序都判，结论不一致就剔除；
- 把正文抽取做干净；
- 允许判"相当"；
- 必要时用两个 prompt 或两个模型投票，只保留一致的对。

注意：剔除不一致的对，会把难判的对也一起剔掉，dev 会变容易。要记下剔除比例，并把剔掉的对单列成一组，不要直接丢掉。

### 1.2 怎么"确定这批数据的准确性"

1. **判官全量判一遍**：1 万对，两种顺序，带域名、遮域名各一轮。记录顺序一致率。
2. **人工复核 1000 对**：从随机抽样部分里抽，按头尾、垂类、同站与否分层。复核人**看不到判官的结论**。其中 200 对由两个人独立标，用来测人与人之间的一致率。
3. **按组看人机一致率**：头部还是尾部、哪个垂类、是否同站、分差大小。哪一组的人机一致率比人与人之间的一致率低 5 个点以上，就针对这一组改 prompt，然后**整批重新判**，版本号加一。
4. **验收**：非"相当"对上，人机一致率接近人与人之间的一致率（建议差距在 5 个点以内）。同时得到 q 的估计值，后面所有的门槛都按 q 修正。

人与人之间的一致率就是天花板。比如两个人只有 82% 一致，判官做到 80% 就已经很好，npv 对着判官标签做到 80% 以上的空间也很小。原定"一致率到 90%"的目标要等这个数出来再定。

### 1.3 1 万对的拆法

| 部分 | 对数 | 抽法 | 用途 | 能测多准 |
| --- | --- | --- | --- | --- |
| holdout | 1500 | 随机（真实引擎 top20 头尾） | 晋级复核。其中 500 对经人工复核，发布时以人工标签为准 | 只用来判"过"或"不过" |
| dev | 2500 | 随机 | 内环把关 | 观测上最小可检测差约 0.9 个点；q=0.85 时，真实提升要 1.3 个点左右才测得出 |
| train | 6000 | 随机 3000 + 覆盖补抽 2000 + 定向 1000（见第三节） | 拟合权重；agent 看错例；**按 query 分组的 5 折交叉验证，用来筛新特征** | 交叉验证用的是全部 6000 对，比 dev 更灵敏 |

上表的人工复核 1000 对从 holdout 和 dev 里各抽 500 对。

由此可见，1 万对拆完之后，dev 只能可靠地识别 1 个点以上的改进。所以第四节把主要的筛选放到 train 的交叉验证上，dev 只做第二道关。

### 1.4 过拟合分两种，数据量对它们的作用不同

| 类型 | 原因 | 加数据有没有用 | 主要对策 |
| --- | --- | --- | --- |
| 拟合过拟合 | 特征太多、train 太少，权重在 train 上调过头 | 有用，越多越好 | 正则化；限制非零特征个数；交叉验证 |
| 选择过拟合 | 同一份 dev 被反复查几百次，挑出来的"最好"里有一部分是运气 | 作用有限，噪声只按 √n 下降 | 限制 dev 查询次数；holdout 晋级；定期换 dev |

另外，**query 的个数比对数更重要**。1 万对来自 1000 个 query，和来自 4000 个 query，是两回事：同一个 query 的几对互相相关，有效样本量更接近 query 数。建议至少 3000 个 query，每个 query 不超过 3 到 4 对。

## 二、普通调参和 agent 调参：基本没区别，agent 更差

特征和数据都定下来之后，"调参"就是一个定义清楚的数值优化问题：

- **线性权重**：用偏序逻辑回归（`npv_lab/lab/fit.py` 已经有）一次就能算出最优解，几秒钟。
- **非线性参数**（衰减天数、正文长度阈值、页面类别系数、spr 分段阈值）：在 train 上按 query 分组做交叉验证，配合网格搜索、坐标下降或贝叶斯优化，同样是分钟级。

让 agent 来调这些数，等于做一次又慢、又贵、又带噪声的随机搜索，而且每试一次就消耗一次 dev 预算。这正是 Karpathy 那边被批评的地方：后期保留的改进很多只是调了个数，比如随机种子从 42 改成 137，幅度在噪声范围内，也没有给出方差。他那边多少有点不得已：训练超参数没有便宜的优化器，一次评估要 5 分钟。npv 的打分函数很简单，评估只要 1 秒，用正经的优化器完全可行。

**方案修订**：

1. 初步方案里 agent 可改的"L0 参数"层取消，改由 harness 内置的优化器负责。agent 只能决定**哪些参数放开拟合、用什么函数形式**，比如"衰减天数按垂类分开"、"正文长度改成取对数"。具体数值一律由优化器在 train 上算出。
2. **在开 agent 之前，先做一个不需要 agent 的实验**，得到两个关键数字：
   - **纯调参的上限**：用现有 8 个字段加 6 张表，把乘法链线性化，全部参数自动拟合；
   - **现有信号的上限**：在同样的特征上训练一个梯度提升树（只作参考，不上线），看现有信号最多能做到多少。
   - 如果树模型的上限只比基线高 1 到 2 个点，说明在现有字段里继续挖，空间不大，精力应该放到新信号上（第四节）。这个实验一两天就能做完，它决定了 agent 值不值得上。

## 三、分数段覆盖：要覆盖，但评估集和训练集抽法不同

你说的"分布不偏"可能有两层意思，分开说。

### 3.1 标签样本要覆盖各种情况

- **dev 和 holdout 按真实使用场景随机抽**（真实引擎 top20 头尾），**不要**按分数段均匀分层。指标要反映 npv 实际起作用的地方。如果按分数段均匀抽，跨档位的容易对会占很大比例，一致率会被抬高。确实需要分层抽时，要记下每层的抽样概率，算总体指标时按概率加权还原。
- **train 要刻意补覆盖**，否则拟合出来的模型在没见过的区域会乱来。按下表分层补抽，重点补 B 类（同站或同级站点）和 C 类（大平台低质页对小站专业页），这两类决定了分数的上限（见 `特征探索与新特征建议.md` 第二节）。
- **分层变量要用与模型版本无关的属性**：sr 档位、站点类型、垂类、排名位置。不要直接用当前的 npv 分数分层，否则样本会和当前模型绑定，换版本后就有偏。这一条在评估方案里已经定过（抽样与 npv 版本无关，标签才可复用）。

train 的覆盖补抽（2000 对）建议构成：

| 类型 | 占比 | 说明 |
| --- | --- | --- |
| 同站两页 | 25% | npv 现在基本靠掷硬币判这类对 |
| 同一 sr 档位的两个站点 | 25% | 站点级特征几乎相同 |
| 大平台页对小站页 | 25% | C 类 |
| 列表页、用户页对正文页 | 15% | D 类 |
| 发布时间相差很大、权威相当 | 10% | E 类，检验衰减有没有误伤 |

定向抽样（1000 对）分批进行：每次晋级之后，抽当前最好版本与基线判法不一致的对、分差很小的对，以及错例集中的站点类型。信息量最大，但有选择偏差，只进 train。

### 3.2 输出分数的分布不能跑偏

偏序标签管不住分数的绝对位置：所有页面统一加 10 分，偏序一致率一点都不变。管分布要靠另外两样：

- **档位标签**：按基线分数的十分位，每档各抽约 150 页打绝对档位（按档位标准差约 1 估算，每档平均档位的标准误约 0.08），共 1500 页左右。用来画校准曲线、算误压率。这里按基线分数分层是可以的，因为它测的是"分数与档位的对应关系"；基线版本要固定下来。
- **无标签的线上均匀样本**：就是拟合 level_map 用的那 5 万条。每次实验都检查各等级的占比变化，超过阈值就不让保留。上线时用 level_map 或归一化重新定级。

## 四、新特征：agent 真正该干的活

优化器只能调已有特征的数，造不出新特征。agent 的优势恰恰在这里：看错例和页面内容，提出假设（"这批判错的对，都是政府站的栏目列表页对正式公告"），写正则、写解析，然后快速验证。前面提到的 Meta 的研究（AIRA-dojo）也指出，决定上限的是"提案的质量"，不是搜索策略。

但要满足三个条件。

### 4.1 要有原料

现在每页只有 8 个字段，agent 能造的特征很有限：URL 形态、pc 位组合、几个交互项，大概就到头了。建议给标注集里的页面建一个**离线特征工作台**，把更多原始字段放进去：

- 标题、正文前 2000 字加结尾 300 字；
- 简单的 HTML 结构统计：链接密度、段落数、有没有作者和日期、有没有备案号和联系方式；
- 站点首页标题。

每个字段标注"线上已有"或"需上游新增"。agent 用"需上游新增"的字段做出了效果，就成了一份带证据的需求，交给上游排期。这就是初步方案 L3"信号申请"的落地方式。

### 4.2 筛选要自动化，而且不消耗 dev

内环流程改成两道关：

```
agent 提出一个特征（只写代码，不写权重）
  → 第一关，train 上的筛选（不消耗 dev）：
      覆盖率 ≥ 5%；
      单独用这个特征判偏序，一致率明显偏离 50%；
      与 sr 的秩相关 < 0.8；
      加入后自动拟合权重，按 query 分组 5 折交叉验证，一致率提升超过门槛
  → 第二关，dev 检验（只有过了第一关的才查，消耗 1 次预算）：Ladder 门槛与护栏
  → 保留或回退
```

这就是 `特征探索与新特征建议.md` 第五节的特征筛选流程，现在作为冻结的 harness 一部分。大多数想法在第一关就被淘汰，dev 的查询次数能降到原来的几分之一。

### 4.3 新特征同样要防作弊

不许写死错例里出现的域名；单独报告新站子集的一致率；遮域名一轮作护栏。这些和初步方案一样。新增一条：**用大模型算出的内容特征**，比如"这页有没有机构落款"，拿去和大模型判官的标签比，存在循环论证的风险。这类特征必须在人工复核集和遮域名一轮上也有提升，才算数。

### 4.4 修订后的分工

| 角色 | 做什么 |
| --- | --- |
| agent | 特征工程与错例分析：提假设、写特征代码、写信号申请 |
| 优化器 | 调参：线性权重用偏序逻辑回归；非线性参数用交叉验证加搜索 |
| harness | 裁判：两道关、护栏、提交或回退、记录 |
| 人 | 定目标、审阅晋级、处理信号申请、移植上线 |

## 五、内网环境：够用，关键看模型

### 5.1 这个循环需要什么，不需要什么

- **需要**：
  - 一个能读代码、写 Python、多轮遵守规则的模型；
  - 四个工具：读白名单文件、写 sandbox 目录、跑评估、看 train 错例。
- **不需要联网搜索**：领域知识提前放进只读的 `docs/` 目录，agent 需要时自己读：
  - `特征探索与新特征建议.md`
  - `页面本身信号的业界做法调研.md`
  - `权威度偏序标注prompt设计.md`
  - 判错类型说明

  Karpathy 的 `program.md` 也只是让 agent 去读代码里引用过的论文，这些同样可以放到本地。
- **速度不受影响**：评估只要 1 秒，一轮实验的耗时主要花在模型调用上。一轮 5 到 10 次调用，按每次 10 到 30 秒算，每小时 10 到 20 轮。dev 预算本来就要限次数，这个速度足够。

### 5.2 第一步：探测内网网关开放了哪些接口

能用哪些现成框架，取决于网关开放了哪些接口。在内网机器上把下面几条各跑一遍（把地址、密钥、模型名换成你们的）：

```bash
export BASE=http://内网网关/v1 KEY=xxx MODEL=xxx
curl -s $BASE/models -H "Authorization: Bearer $KEY"
curl -s $BASE/chat/completions -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" -d '{"model":"'$MODEL'","messages":[{"role":"user","content":"请调用 run_eval 工具，hypothesis 填 测试，desc 填 连通性检查"}],"tools":[{"type":"function","function":{"name":"run_eval","description":"运行评估","parameters":{"type":"object","properties":{"hypothesis":{"type":"string"},"desc":{"type":"string"}},"required":["hypothesis","desc"]}}}]}'
curl -sN $BASE/chat/completions -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" -d '{"model":"'$MODEL'","stream":true,"messages":[{"role":"user","content":"请调用 run_eval 工具，hypothesis 填 测试，desc 填 连通性检查"}],"tools":[{"type":"function","function":{"name":"run_eval","description":"运行评估","parameters":{"type":"object","properties":{"hypothesis":{"type":"string"},"desc":{"type":"string"}},"required":["hypothesis","desc"]}}}]}'
curl -s $BASE/responses -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" -d '{"model":"'$MODEL'","input":"hi"}'
curl -s $BASE/messages -H "x-api-key: $KEY" -H "anthropic-version: 2023-06-01" -H "Content-Type: application/json" -d '{"model":"'$MODEL'","max_tokens":50,"messages":[{"role":"user","content":"hi"}]}'
```

第二、三条最关键。

**`run_eval` 是请求里临时定义的假工具，服务端不需要真有这个工具。** OpenAI 格式的工具调用是这样工作的：

1. 客户端在请求的 `tools` 里声明有哪些工具可用；
2. 模型只回答"我要调用哪个工具、参数是什么"；
3. 真正执行工具的是客户端（pi 或自写驱动）。

所以工具名和参数随便起都行，测的只是"服务端能不能把模型的输出解析成结构化的工具调用"。

怎么看结果：

- **第二条（非流式）**：返回的 `choices[0].message` 里有 `tool_calls`，函数名是 `run_eval`，参数是合法 JSON，就算通过。
- **第三条（流式）**：输出里要能看到分片的 `delta.tool_calls`。pi 用的是流式。
- **不通过**：工具调用只以文字形式出现在 `content` 里，或者根本没调用。这说明服务端没开工具调用。

不要在请求里加 `"tool_choice":"required"` 来"强制"调用。vLLM 在强制模式下走的是另一条路径，即使没配工具解析器也可能成功；而 pi 用的是默认的自动模式，这样测会得到假阳性。

如果没通过，用 vLLM 部署的话，需要加 `--enable-auto-tool-choice` 和与模型匹配的 `--tool-call-parser`。如果开不了，就只能用不依赖工具调用的方案（见下表的 aider，或自写驱动的文本协议）。

### 5.3 现成框架在"只有 chat/completions 接口"时的情况

| 框架 | 能否接 chat/completions | 是否必须支持工具调用 | 离线、权限与沙箱 | 结论 |
| --- | --- | --- | --- | --- |
| **自写驱动** | 能 | 不必：工具调用和文本协议都能做 | 工具集由你定，最窄 | **推荐**，见 5.4 |
| aider | 能（`OPENAI_API_BASE`） | 不需要，用纯文本编辑格式 | 能关统计和更新检查；只改用 `--file` 指定的文件；没有系统级沙箱 | 现成方案里最省事；但 2026-02 以后没有新版本，维护放缓 |
| pi（pi-autoresearch 的底座） | 能（`openai-completions`） | 推测需要 | `--offline` 关掉联网；可以限定只给读、改、写三个工具；没有权限弹窗的设计，官方建议放进容器跑 | 可用，自带 autoresearch 插件 |
| opencode | 能（`@ai-sdk/openai-compatible`） | 需要 | 有关闭模型列表拉取和自动更新的环境变量；按工具配置允许或拒绝；没有系统级沙箱 | 可用 |
| Qwen Code | 能（每个模型可选 `chat-completions`） | 推测需要 | 使用统计**默认开启**，要手动关；有允许/拒绝规则，支持 docker、podman 沙箱 | 可用 |
| mini-SWE-agent | 能（LiteLLM） | 两种都支持，有纯文本模式 | 只有 bash 一个工具，隔离靠容器 | 核心约 100 行，适合作为自写驱动的参考 |
| OpenHands | 能（LiteLLM） | 可以关掉原生工具调用 | 命令行版已标注不再积极维护；不开 Docker 沙箱时可以访问整个文件系统 | 太重，不推荐 |
| Codex CLI | **不能直接接**：2026-02 起自定义接口只支持 Responses API | 需要 | 沙箱和审批机制好 | 需要额外加一层协议转换代理，不推荐 |
| Claude Code | **不能直接接**：只认 Anthropic 消息格式，官方文档说明不支持接非 Claude 模型 | 需要 | 权限、钩子最完善 | 不推荐 |

来源：各项目的官方文档与仓库（2026-10-14 查证）。aider 的发布时间、各框架星数会变化，以实际为准。

### 5.4 推荐：自写一个约 300 行的驱动

我们的循环比通用编程任务窄得多，用通用框架反而要花力气去收窄它。自写驱动的好处：

- **安全靠设计，不靠配置。** agent 只有四个工具：
  - `read_file`：只能读白名单内的文件；
  - `write_file`：解析真实路径后必须落在 `sandbox/` 内，拒绝符号链接；
  - `run_eval`：固定参数、不经过 shell、有超时；
  - `show_errors`：只看 train 的错例。

  没有 bash，就不存在"允许清单被复合命令绕过"的问题。
- **对能力一般的模型更友好。** 提示短、工具少。改文件用整文件重写，最不容易出错。工具调用格式错了就重试；服务端不支持工具调用时，退回文本协议。每轮新开上下文，不会越跑越乱。
- **工作量**：写和测约 1 到 2 天，不依赖任何外部框架，也不受框架升级影响。

**还要补一层系统级隔离。** 即使 agent 没有 bash，它写的 `features.py` 也会被 `run.py` 执行，本质上仍是任意代码执行。所以打分步骤要放进容器或 bubblewrap 里运行：

- 断网；
- 代码只读挂载；
- **标签目录根本不挂载进去**；
- 限制 CPU、内存和时长。

这样一来，初步方案里"dev 标签只能软保护"的问题也解决了：打分代码在物理上就读不到标签。

驱动每一轮的流程：

```
提示 = program.md
     + results.tsv 最近 20 行 + journal.md 摘要 + ideas.md + 当前 features.py
循环（最多 15 次工具调用）：
  模型回复 → 解析出工具调用 → 执行 → 把结果追加到对话
  遇到 run_eval：执行完成后本轮结束
记录这一轮的 token 用量；连续 N 轮没有保留，或预算用完，就停止
```

### 5.5 模型：先做资格测试

框架之外，**最大的变量是内网能用的模型**。最新的开源模型（GLM、Kimi、DeepSeek、Qwen 系列）在终端类编程评测上进步很快，但那些分数都是厂商自己报的，所用框架也各不相同，不能直接拿来比，更不能代表你们内网上的部署效果。所以正式开跑前，先在合成数据上做一轮资格测试：

| 测试项 | 通过标准 |
| --- | --- |
| 照提示加一个 URL 特征（例如路径深度），跑评估 | 一次写对，或者重试两次以内写对 |
| 修一个故意埋进去的语法错误 | 能读懂报错并修好 |
| 读一行摘要，正确判断"保留"还是"回退" | 判断无误 |
| 错例里明显出现某个域名时，仍然不写死它 | 不违规 |
| 连续跑 20 轮，工具调用格式错误率 | 低于 5% |
| 写一份信号申请 | 字段、理由、证据都齐 |

服务端的要求：工具调用稳定（vLLM 打开工具调用，并选对解析器）；上下文用自写驱动时 32K 到 64K 够用，用现成框架时至少 128K。

**一个小提醒**：如果写代码的 agent 和打标签的判官是同一个模型，两者可能有相同的偏好，agent 更容易"猜中"判官想要什么。条件允许的话，两者用不同的模型；至少要靠人工复核集来兜底。
