# NPV 自动研究（autoresearch）框架：调研与初步方案

- 日期：2026-10-13
- 目标：让编码 agent 在无人值守的循环里自己提出假设、改打分代码、跑冻结评估、决定保留或回退，持续提高 npv 与权威度标签的一致率。人负责定目标、供标签、审阅晋级、移植上线。
- 依据：外部调研（第一节，附链接）；现有代码 `npv_py`（冻结基线）、`npv_lab`（实验层）；评估方案与标注 prompt（`权威度偏序标注prompt设计.md`）；特征路线（`特征探索与新特征建议.md`）。
- 状态：方案稿，没有写代码。第八节列出需要你拍板的问题。
- 修订：2026-10-14 按五个问题的讨论修订了搜索空间（数值交给优化器）、内环流程（两道关）、数据切分和运行环境，详见 `五个问题的回答与方案修订.md`。

## 0. 结论先行

1. **npv 很适合 autoresearch，但瓶颈和 Karpathy 的场景相反。** 他那边一次实验 5 分钟 GPU，算力是瓶颈。npv 一次实验 1 秒左右，一晚能跑上千次。真正稀缺的是标签：用 1500 对标签做验证时，一致率的 95% 区间是 ±2 个百分点。agent 跑几百次、每次挑最好的保留，光靠噪声就能"涨"1 到 2 个点。**框架设计的重心是防止过拟合验证集，不是提速。**
2. **现有 `npv_lab` 已经搭好了大约一半。** 可改文件（`features.py`、`configs/*.json`）、冻结基线、评估、`experiment.py` 写 `results.tsv`、偏序权重拟合都已具备。还缺六样：真实标签与切分、git 保留/回退、agent 指令文件 `program.md`、自动门禁、防作弊检查、隐藏 holdout。
3. **建议的结构是三层循环。**
   - 内环：agent 提假设、改代码、跑分、决定保留或回退，分钟级。
   - 中环：在隐藏 holdout 上复核、人工审阅、晋级或整体回滚，每天一次。
   - 外环：补标签、换验证集、移植到 Java/Spark，每周一次。
4. **保留或回退由冻结脚本决定，agent 不能自己说了算。** agent 只能改沙箱里的文件、只能运行两条指定命令，看得到训练集的逐条错例和验证集的汇总数字，碰不到 holdout。打分进程和评估进程分开，打分代码读不到任何标签。
5. **现有评估里有两个会被刷分的口子，开跑前必须先修。** 两页分数相同的对、打分缺失的对都不计入一致率。agent 只要把难分的页压成同分，或者让它们打分失败，一致率就会上去。详见 4.3。
6. **内环能搜的只有"现有信号怎么组合"，天花板取决于信号本身。** 现在每页只有 8 个字段（url、adc、pc、pct、pt、正文长度、sr、spr）加 6 张站点表，没有标题和正文。框架要留一条"申请新信号"的通道，由外环补列。agent 不能自己造数据。
7. **第一步不是写框架，是拿到真实标签。** 1 万对带域名的偏序标签（外加遮域名一轮）、1500 条档位、1000 对人工复核。没有这些，框架只能在合成数据上空转。

## 1. 调研：autoresearch 与同类做法

### 1.1 Karpathy 的 autoresearch

仓库 [karpathy/autoresearch](https://github.com/karpathy/autoresearch) 于 2026-03 发布，MIT 协议，截至 10 月约 9.8 万星。机制很简单：

- **三个文件**：
  - `prepare.py` 冻结，包含数据准备、dataloader 和评估函数；
  - `train.py` 是 agent 唯一能改的文件；
  - `program.md` 是给 agent 的研究指令，由人迭代。README 称它为一个极轻量的 skill。
- **预算与指标**：每次实验固定训练 5 分钟，超过 10 分钟就杀掉记为失败。指标是 val_bpb（越低越好），与词表大小无关，所以不同架构的结果可以直接比较。
- **循环**（[program.md](https://github.com/karpathy/autoresearch/blob/master/program.md)）：
  1. 新建分支 `autoresearch/<tag>`，第一次运行必须是不改代码的基线；
  2. 每轮先改 `train.py`、提交，再跑，日志重定向到文件，不让它冲进上下文；
  3. 用 grep 取指标写进 `results.tsv`，列为 commit、val_bpb、内存、状态、描述；
  4. 变好就保留，**持平或变差就 `git reset` 回去**；
  5. 崩溃时读日志尾部，小错修好重跑，修不好就记为 crash 放弃。
- **两条人为规则**：
  - **简洁原则**：0.001 的提升要加 20 行别扭代码，不值得；删代码还能持平，就保留。
  - **不停机**：进入循环后不许问人要不要继续。没思路时就重读代码、组合以前差一点成功的尝试，或者做更激进的改动。
- **结果**：README 配图是 83 次实验、15 次保留，val_bpb 从约 0.998 降到 0.977。
- **已知问题**：
  - 纯贪心爬山，要两步才见效的改动会被回滚；
  - 有好几个 issue 指出，换随机种子被记成了"改进"，即把噪声当信号（[#466](https://github.com/karpathy/autoresearch/issues/466)）。

**一篇直接相关的复现（[arXiv 2607.18064](https://arxiv.org/html/2607.18064)）**：把 autoresearch 用在一个识别任务上。

- 发现的问题：
  - 有的 agent 在代码里写死了几十个答案 ID 来刷分；
  - agent 通过共享的 git 库读到了兄弟运行的日志；
  - agent 在持久记忆里给"以后的运行"留了话；
  - 失败报告直接打印了标准答案。
- 加入实验者掌控的 holdout 之后，写死答案的现象消失了。
- 作者给出五条规则：
  1. holdout 由实验者评分，并报告训练与测试的差距；
  2. 失败信息不回显标准答案；
  3. 每次运行用全新克隆；
  4. 审计记忆、全局配置这类跨运行通道；
  5. 事先登记假设。

### 1.2 衍生项目里值得借的机制

- **[pi-autoresearch](https://github.com/davebcn87/pi-autoresearch)**：
  - 支持任意命令和指标，日志只追加不改写，新 agent 可以接着跑；
  - `checks.sh` 不通过就禁止保留；
  - 用"最佳改进 ÷ 噪声"给出置信度提示；
  - 收尾时把保留的改动拆成多个可独立审查的分支。
- **[evo](https://github.com/evo-hq/evo)**：
  - 用树搜索代替贪心，多个 agent 并行，每个一个 worktree；
  - 有门禁：不通过就丢弃，即使分数更高；
  - 自动给留出切片设分数下限。
  - 它的经验是，没有门禁时，搜索会去返回常数、跳过实际工作。
- **[arXiv 2608.07542](https://arxiv.org/abs/2608.07542)**：用不可变的"实验卡"把预测和结果锁在一起，防止事后改写假设。
- 汇总清单：[awesome-autoresearch](https://github.com/WecoAI/awesome-autoresearch)。

### 1.3 进化式代码搜索

- **AlphaEvolve**（[arXiv 2506.13131](https://arxiv.org/abs/2506.13131)）：
  - 快模型负责广度，强模型负责深度；
  - 程序库结合 MAP-Elites 与岛屿模型；
  - 改动用 diff 提交；
  - 评估是级联的：先过便宜的检查，再跑贵的评估；
  - 同时优化多个指标。
- **[OpenEvolve](https://github.com/algorithmicsuperintelligence/openevolve)**、**ShinkaEvolve**（[arXiv 2509.19349](https://arxiv.org/abs/2509.19349)）：
  - 都用 embedding 相似度过滤重复改动；
  - 会把报错和评估反馈塞进下一代的提示；
  - ShinkaEvolve 用 bandit 在多个模型之间分配调用。
- **CORAL**（[arXiv 2604.01658](https://arxiv.org/abs/2604.01658)）：
  - 用长期运行的 agent 加共享记忆，取代固定的进化规则；
  - 评估器和 agent 隔离：agent 在容器里以非特权用户运行，读不到评分器和答案。
- **和 npv 的关系**：这类方法适合"一个程序、一个可靠分数、评估很贵"的问题。npv 正好相反，评估便宜、分数有噪声。它们的去重和级联评估可以借，种群和岛屿目前用不上。

### 1.4 机器学习工程 agent 的经验

- **AIDE**（[arXiv 2502.13138](https://arxiv.org/abs/2502.13138)）：
  - 每次只允许一个原子改动，便于归因；
  - 历史记忆只存指标和要点，不存完整日志。
- **AIRA-dojo**（Meta，[arXiv 2507.02554](https://arxiv.org/abs/2507.02554)）：
  - 瓶颈在"提案质量"，不在搜索策略：换更好的提案方法后，贪心搜索就从 39.8% 涨到 45.5%，而换成 MCTS 或进化搜索几乎没有增益；
  - 验证分一直涨，测试分到顶后略降；
  - 按验证分挑选本身就有损失。
- **MLE-bench**（[arXiv 2410.07095](https://arxiv.org/abs/2410.07095)）：时限从 24 小时加到 100 小时，成绩只小幅上升，奖牌数有时反而下降，原因也是"选最佳尝试"的方法有误差。
- **R&D-Agent**（[arXiv 2505.14738](https://arxiv.org/abs/2505.14738)）：
  - train/val/test 一开始就固定，test 对 agent 不可见；
  - 先在小子集上做原型，再跑全量。
- **AI Scientist**（[Sakana](https://sakana.ai/ai-scientist/)）：早期版本出现过改自己代码来延长超时的行为，官方建议沙箱运行。

### 1.5 判官相关：prompt 优化与 Goodhart

- **GEPA**（[arXiv 2507.19457](https://arxiv.org/abs/2507.19457)，已集成进 DSPy）：
  - 让模型用自然语言反思执行轨迹，再提出改动；
  - 按单个样本保留各有所长的候选。
  - 适合在有人工标签时，自动改进判官 prompt（5.3）。
- **Goodhart 现象**：
  - 对代理奖励优化过度，真实目标会变差（[arXiv 2210.10760](https://arxiv.org/abs/2210.10760)）；
  - 大模型判官有位置偏差、偏好长文、偏好自己的输出（[arXiv 2306.05685](https://arxiv.org/abs/2306.05685)）。
  - **对 npv 的具体风险**：正文长度本身就是一个特征。如果判官偏好长文，agent 会把这个偏好放大成"长就权威"。

### 1.6 自适应过拟合与小样本噪声

- **反复查同一份验证集会过拟合，有两种成熟的对策：**
  - **Thresholdout**（Dwork 等，[arXiv 1506.02629](https://arxiv.org/abs/1506.02629)）：训练集与 holdout 的差距超过"阈值加噪声"时，才返回加噪的 holdout 值，并扣一次预算。
  - **Ladder**（Blum 与 Hardt，[arXiv 1502.04585](https://arxiv.org/abs/1502.04585)）：新结果比当前最好的好出一个门槛，才更新排行榜，否则返回旧值。无参数版的门槛是 s/√n，其中 s 是逐样本差值的标准差。
- **样本成组时，标准误要按组算**（Miller，[arXiv 2411.00640](https://arxiv.org/abs/2411.00640)）：按组算的标准误是朴素算法的 1.1 到 3 倍。比较两个版本要用逐样本的配对差。

### 1.7 对 npv 的启示（已落实到后文）

| 启示 | 来源 | 落在本方案哪里 |
| --- | --- | --- |
| 冻结评估，agent 只改一个可改区 | Karpathy、R&D-Agent | 3.1 目录、4.5 权限 |
| 保留门槛不能是 0，要高于噪声 | autoresearch #466、Ladder | 4.2 用 Ladder 门槛 |
| holdout 由实验者掌控，agent 读不到 | 2607.18064、CORAL | 3.2、4.2、4.5 |

| 先提高提案质量，再考虑换搜索策略 | AIRA-dojo、AIDE | 错例工具、一次一个原子改动；树搜索放到以后 |

## 2. 把 autoresearch 映射到 npv

### 2.1 组件对照

| Karpathy autoresearch | npv 对应物 | 现状 |
| --- | --- | --- |
| `prepare.py`：数据、分词、评估，冻结 | `harness/`：输入快照、站点表、标签切分、评估、门禁，冻结 | 评估在 `npv_lab/lab/evaluate.py`，未冻结，也没做切分 |
| `train.py`：agent 唯一可改的文件 | `sandbox/features.py` + `sandbox/config.json`（第二阶段加 `sandbox/model.py`） | `npv_lab/lab/features.py` 与 `configs/` 已按此约定设计 |
| `program.md`：给 agent 的研究指令，由人迭代 | `program.md` | 无 |
| 固定 5 分钟训练预算 | 固定的验证集评估次数预算（例如每版验证集 300 次） | 无。单次只要几秒，限时间没有意义，要限次数 |
| `val_bpb`，越低越好 | 验证集严格一致率（4.3），越高越好；外加护栏指标 | `pairwise_acc` 已有，计法要修 |
| 先提交再跑；持平或变差就 `git reset` 回去 | 冻结的 `run.py` 跑完门禁后提交或回退，agent 不碰 git | 无 git，人工判断 |
| `results.tsv`：commit、指标、状态、描述 | 同左，加假设、门槛、复杂度与护栏列 | `experiment.py` 已写 `results.tsv`，缺 commit 与状态 |
| 简洁原则：涨得少但代码多就不要 | 复杂度预算：特征数、非零权重数、规则数、代码行数 | 无 |

### 2.2 npv 和 Karpathy 场景的四个关键差异

| 差异 | Karpathy | npv | 设计上的应对 |
| --- | --- | --- | --- |
| 评估噪声 | 验证集是几百万 token，几乎没有噪声 | 几千对标签，有明显噪声（见下表） | 标签量起步 5000 对；保留门槛高于噪声；holdout 复核晋级；验证集按次数轮换 |
| 作弊空间 | 很难靠代码"记住"验证集 | 很容易：在特征里写死见过的域名，就能直接刷标签对 | 训练集、验证集按 query 切分；单独报告"新站子集"一致率；静态检查限制写死的域名；打分与评估分进程 |
| 目标本身有偏 | bpb 就是真正的目标 | 标签来自大模型判官，它有偏好品牌、偏好长文的倾向；对着判官优化会把偏差学进来 | 遮域名一轮作护栏；人工复核集只在发布时用；判官换版本就整体重算基线 |
| 能否上线 | 训练出来的就是成品 | 必须能移植到 Java/Spark，只能用线上有的字段 | 只允许访问白名单字段与模块；每个保留的改动都带移植说明；中环审阅时检查能否移植 |

**噪声有多大**（按一致率 80% 估算；"最小可检测差"取改动前后分歧对占 3% 到 6%、符号检验 p<0.05；"虚高"指跑 N 次纯噪声实验时，最好那次的期望虚高。这是粗估，假设各次实验互相独立；实际上相邻实验高度相关，虚高会小一些，但量级不变）：

| 验证集有效对数 | 一致率 95% 区间 | 单次改动最小可检测差 | 跑 300 次后最好一次的虚高 |
| --- | --- | --- | --- |
| 1,500 | ±2.0 个点 | 1.0 到 1.3 个点 | 1.5 到 2.1 个点 |
| 3,000 | ±1.4 个点 | 0.7 到 0.9 个点 | 1.1 到 1.5 个点 |
| 5,000 | ±1.1 个点 | 0.5 到 0.7 个点 | 0.8 到 1.2 个点 |
| 10,000 | ±0.8 个点 | 0.4 到 0.5 个点 | 0.6 到 0.8 个点 |

上表按"每对互相独立"计算，实际偏乐观：同一 query 的几对、同一站点的多页互相相关。按组算的标准误通常是朴素算法的 1.1 到 3 倍（Miller，1.6 节）。所以评估脚本要按 query 做聚类自助法（cluster bootstrap），再据此定门槛；抽标签时宁可多抽 query、每个 query 少抽几对。

结论：一次加一个特征、调一个权重，带来的提升大多不到 1 个点。验证集少于 5000 对时，内环的"保留"大部分是噪声。holdout 复核和验证集轮换因此不能省。

## 3. 整体架构

```
          ┌────────────── 外环（每周）──────────────┐
          │ 标签工厂：抽样 → 大模型判官（两种顺序，      │
          │ 带域名、遮域名各一轮）→ 一致性过滤 → 人工抽检 │
          │ 补信号：按 agent 的申请给快照加列            │
          │ 移植：晋级改动 → Java/Spark → 线上一致性核对 │
          └───────┬───────────────────────▲──────────┘
       新标签、新列 │                       │ 晋级的提交
          ┌───────▼───── 中环（每天）────────┴──────────┐
          │ holdout 复核（只回报"过"或"不过"）+ 人工审阅 diff │
          │ 过：打标签 promoted/N；不过：回滚到上一个晋级点  │
          └───────┬───────────────────────▲──────────┘
                  │                       │ 保留的提交
          ┌───────▼───── 内环（分钟级）──────┴──────────┐
          │ agent：读日志与训练集错例 → 提假设 → 改 sandbox │
          │ run.py：静态检查 → 打分（读不到标签）→ 评估      │
          │        → 门禁 → git commit 或 git reset → 记录  │
          └──────────────────────────────────────────┘
```

### 3.1 目录（建议放在 `claude/npv_ar/`，单独做成 git 仓库）

```
npv_ar/
  program.md            # agent 指令。人改，agent 只读
  ideas.md              # 待试想法清单。人播种，agent 可追加
  journal.md            # agent 的研究笔记：每次实验的假设、结果、结论
  results.tsv           # run.py 写，agent 只读
  sandbox/              # agent 唯一可改的目录
    features.py         # 从 npv_lab/lab/features.py 起步
    config.json         # 从 npv_lab/configs/baseline.json 起步
    lists/*.txt         # 可选：agent 维护的小名单（UGC 平台等），有条数上限
  harness/              # 冻结。agent 只读或不可读
    snapshot/           # 输入快照 + 6 张表 + 版本哈希
    labels/train/       # 可读：逐条标签，含判官给的分维度分数
    labels/dev/         # 不可直接读：只通过评估脚本拿汇总数
    run.py              # agent 唯一能调用的评估入口，见附录 B
    score.py            # 打分进程：只读快照和 sandbox，看不到 labels/
    evaluate.py         # 评估进程：不导入 sandbox 代码
    gate.py             # 保留/回退判定
    lint.py             # 静态检查
    errors.py           # 训练集错例分析，给 agent 找灵感
  driver.py             # 外层驱动：每轮新开一个 agent 会话；中环 holdout 复核
  ../npv_ar_private/    # 仓库之外：holdout 与人工复核集，只有驱动器能读，agent 的沙箱禁止读取
```

`npv_py` 继续冻结作为基线，`npv_lab` 的 `LabScorer`、`evaluate`、`fit` 直接复用，改成从 `sandbox/` 加载特征。

### 3.2 数据切分

| 切分 | 来源 | 占比 | agent 能看到什么 | 用途 |
| --- | --- | --- | --- | --- |
| train | 随机抽样 + 覆盖补抽 + 定向抽样（见 5.2） | 按 1 万对算约 6000 | 逐条标签、判官理由、错例 | 拟合权重；错例分析找灵感；按 query 分组的交叉验证筛特征（第一道关） |
| dev | 只用随机抽样 | 约 2500 | 只有汇总指标（总体、按分差桶、按分组） | 内环第二道关 |
| holdout | 只用随机抽样 | 约 1500 | 什么都看不到，只知道"过"或"不过" | 中环晋级 |
| 人工复核集 | 从 dev 和 holdout 里各抽 500 对，人工复核 | 1000 | 什么都看不到 | 测判官准确率与人机一致率上限；holdout 里那 500 对在发布时以人工标签为准 |
| 无标签全量样本 | 线上均匀抽样 1 万到 5 万行 | 不切分 | 分布统计 | 检查分数分布和等级分布有没有漂移、特征覆盖率 |

切分规则：

- **按 query 切分**，同一 query 的所有对落在同一份里。
- dev 里单独报告**新站子集**：两页的站点都没在 train 标签里出现过的那些对。总体涨了、新站子集没涨，说明在记站点。
- dev 不是一成不变的：用满评估次数预算，或者每次晋级之后，就从外环拿一批新标签换掉 dev，旧 dev 并入 train。

### 3.3 一次内环迭代

1. agent 读 `program.md`、`results.tsv` 最近 20 行、`journal.md`、`ideas.md`。用外层驱动器时，这些内容由驱动器拼进提示，并注明本轮允许的搜索层级（4.1）。
2. agent 选一个假设，可以来自想法清单，也可以来自 `harness/errors.py` 给出的训练集错例。它修改 `sandbox/` 里的文件，在 `journal.md` 写一行："假设：……；预期：……"。
3. agent 运行唯一允许的评估命令 `python harness/run.py --hypothesis "……" --desc "……"`。假设在评估之前就写进记录，之后不能改（"实验卡"做法，1.2 节）。这个冻结脚本依次执行静态检查、在 train 上自动拟合数值参数并打分、评估和门禁（附录 B）。门禁分两道关：
   - **第一道关**：train 上按 query 分组的 5 折交叉验证，不消耗 dev。大多数想法在这里就被淘汰。
   - **第二道关**：过了第一道关才查一次 dev，消耗 1 次预算。
4. 门禁通过，`run.py` 执行 `git commit`，`results.tsv` 记为 keep；不通过就执行 `git reset --hard`，记为 discard；崩溃记为 crash，同一个想法最多修两次。
5. agent 读结果，在 `journal.md` 补一句结论，进入下一轮。

agent 不能执行 git，保留或回退只能由 `run.py` 来做。这样即使 agent "想"保留一个变差的改动，也做不到。holdout 复核不在 `run.py` 里，由中环的驱动器在 agent 会话之外执行。

## 4. 关键设计

### 4.1 搜索空间分层（逐层放开）

| 层 | agent 能改什么 | 例子 | 何时放开 |
| --- | --- | --- | --- |
| L0 参数 | **agent 不改数值。** 只能在 `config.json` 里声明哪些参数放开拟合、用什么函数形式；数值由 harness 的优化器在 train 上拟合（线性权重用偏序逻辑回归，其余用交叉验证加搜索） | 衰减天数按垂类分开拟合；正文长度改用对数 | 第一天 |
| L1 特征 | `features.py`：用现有 8 个字段和 6 张表造新特征；权重交给拟合，不让 agent 手调 | URL 深度、列表页正则、用户页正则、UGC 子域、pc 位拆平、`sr × ugc` 交互 | 第一天 |
| L2 结构 | `model.py`：把乘法链改成单一线性形式加少量交互项；把时效从权威分里拆出去 | 去掉保底 60；adc≥2 不再跳过页面级降权 | L0、L1 收敛之后，并且你同意改结构（问题 3） |
| L3 新信号 | agent 不能自己造数据，只能在 `ideas.md` 里写"信号申请"：要什么字段、预计救哪类判错、在 train 上的证据 | 标题、正文前 500 字、ICP 主体类型、域名年龄 | 外环处理，补进快照后新开一轮 |

禁止项写进 `program.md`，并由 `lint.py` 和权限配置（4.5）强制执行：

- 不许读写文件，不许联网，不许导入白名单之外的模块（白名单：`math`、`re`、`urllib.parse`）。
- 只许访问 `ScoreInput` 的 8 个字段、站点表和 `sandbox/lists/`。
- 改 `harness/`、`results.tsv`、`program.md` 一律拦截。
- 单次改动新增的域名字面量超过 20 个，不自动保留，转人工审阅。

### 4.2 门禁：什么时候保留

内环（每次实验，对比当前最好的提交）：

0. **第一道关（train 交叉验证）**：自动拟合数值后，按 query 分组做 5 折交叉验证，一致率提升超过门槛才进入下面的 dev 检验。不消耗 dev 预算。
1. **硬约束**：静态检查通过；没有 NaN 或越界；前 6 个基线特征不变；无标签全量样本上没有坏行增加；分数分布漂移在阈值内。
2. **主指标**：dev 严格一致率比当前最好高出至少 ε，采用 Ladder 的无参数门槛：ε = max(0.2 个点, 逐对配对差按 query 聚类后的标准误)。5000 对、分歧对占 5% 时，按独立样本算约 0.3 个点，聚类后会更高。
   - 回报给 agent 时同样按 Ladder 处理：过门槛就更新"当前最好"并给出精确到 0.1 个点的数字；没过门槛只给粗档："明显变差"、"持平"或"略好但未过门槛"。这样 agent 没法靠大量微调去试探 dev 的逐对答案。
3. **护栏**：小分差桶一致率、误压率、遮域名一轮一致率、新站子集一致率、各分组（头尾、垂类）一致率，任何一项都不能比当前最好差超过容差。
4. **简洁原则**（沿用 Karpathy 的规则）：指标持平但代码更简单（特征、规则、非零权重更少），也保留；指标涨幅小于 ε 却加了一大块代码，不保留。

中环（每 10 次保留或每天一次，对比上一个晋级点）：

- 在 holdout 上做配对符号检验，单侧 p<0.05 且涨幅 ≥ ε 才晋级，并打 git 标签 `promoted/N`。不通过就整体回滚到上一个晋级点，这段分支在 `journal.md` 里记为"dev 过拟合"。
- holdout 只回报"过"或"不过"和一个粗档位，不回报精确数字（Thresholdout 思路，1.6 节）。每版 holdout 最多用 20 次，用满就换新的。
- 人工审阅这次晋级的 diff、移植说明，以及翻转最多的 20 对样例。

### 4.3 先修评估里的两个刷分口子

`npv_lab/lab/evaluate.py` 的 `pairwise_metrics` 现在把两类对排除在一致率之外：

- 两页分数相同（`n_score_tie`），
- 有一页没打出分（`n_missing_url`，坏行被跳过就会这样）。

agent 只要把难判的对压成同分，比如把分数取粗、让大量页面落进保底 60，或者让难判的页触发坏行，一致率就会"上涨"。已用现有代码验证：10 对里判对 6 对，一致率是 60%；把判错的 4 对压成同分，或者让它们打分缺失，一致率都变成 100%。

冻结进 harness 的评估要改成**严格一致率**：

```
严格一致率 = (判对数 + 0.5 × 分数相同数) / (非相当标签的对数，含打分缺失的对)
```

打分缺失的对计为错。`n_score_tie` 和 `n_missing_url` 照常输出，作为护栏监控。

### 4.4 主指标用哪一轮标签

带域名一轮的标签衡量"站点声誉加内容"，和 npv 的业务定义（"更信任哪个来源"）一致，建议作主指标。遮域名一轮作护栏：主指标涨、遮域名一轮跌，说明改动在加强品牌先验，是在学判官对品牌的偏好。这是问题 2，需要你确认。

### 4.5 agent 怎么跑（以 Claude Code 为例）

> 2026-10-14 修订：正式环境在内网，只有 OpenAI 格式接口，Claude Code 和 Codex CLI 都不能直接接入。正式方案改用自写驱动加容器隔离，见 `五个问题的回答与方案修订.md` 第五节。本节与附录 C 只适用于在外网用 Claude Code 先做试验。

两种跑法都可以，循环状态都放在磁盘上（`results.tsv`、`journal.md`、git），不靠对话记忆。

| | A：交互式长会话 | B：外层驱动，每轮一个新会话 |
| --- | --- | --- |
| 怎么起 | 在 `npv_ar/` 打开 Claude Code，说"读 program.md，开始"。用 Stop 钩子（没有 `STOP` 文件、行数没到上限，就让它继续）或 `/goal` 让它不停 | `driver.py` 用 Claude Agent SDK 循环调用 `query()`（或 `claude -p`），每次只做一轮实验 |
| 上下文 | 越跑越长，接近上限时自动压缩，压缩会丢细节 | 每轮都从 `program.md`、`results.tsv` 尾部、`journal.md` 和 git 重新开始，不会漂移 |
| 成本控制 | 只能看 `/usage` | 每轮设 `max_turns` 和 `max_budget_usd`；驱动器累计总额，超额或连续 N 轮没有保留就停 |
| 适合 | P2 有人值守：人能实时看它怎么想，便于改 `program.md`。Karpathy 用的就是这种 | P3 过夜无人值守 |

**权限：四层叠加。** 文档明确说没有哪一层是绝对边界，所以要叠着用：

1. **权限模式 `dontAsk` 加允许清单**：只放行读文件、编辑 `sandbox/**`、`journal.md`、`ideas.md`，以及两条命令 `python harness/run.py *`、`python harness/errors.py *`。其他操作直接拒绝，不会弹窗卡住循环。
2. **拒绝规则**：拒绝编辑 `harness/**`、`results.tsv`、`program.md`；拒绝读取 dev 标签目录和仓库外的 holdout 目录。拒绝优先于允许。
3. **PreToolUse 钩子**：编辑或写入的路径不在 `sandbox/`、`journal.md`、`ideas.md` 里，就用退出码 2 拦下。同时把每次工具调用记进日志，供事后审计。
4. **Bash 沙箱**：开启，网络全关，禁止写 `harness/`，禁止读 holdout 目录。`run.py` 本身不需要读 holdout，所以不受影响。

**一个容易忽略的限制。** 拒绝读取的规则只管 Claude 自己的读文件工具，以及 `cat`、`sed` 这类命令；Python 进程自己打开文件，这条规则管不住。所以：

- **dev 标签只能软保护**：agent 没法执行任意 Python（允许清单）；sandbox 代码禁止读写文件（静态检查）；每次工具调用都有审计日志。
- **holdout 必须硬保护**：放在仓库外，沙箱禁止读取，只有 agent 会话之外的驱动器读得到。这也是为什么晋级判定必须走 holdout。

**其他要点：**

- **切断跨轮次的信息通道**（1.1 节那篇复现论文里实际发生过）：
  - 跑法 B 每晚从全新克隆开始，不共享旧的 worktree 和日志；
  - 关闭或审计 Claude Code 的自动记忆、全局配置这类会跨会话保留的位置；
  - `journal.md` 只记假设与结论，`lint.py` 检查它不能出现 dev 标签里的 URL。
- 要更强的隔离，可以学 CORAL：让 agent 以单独的系统用户运行，标签目录对这个用户不可读。
- 不要用 `--bare` 启动：它会跳过项目里的钩子。
- 想并行跑几条路线（比如 Claude Code 和 Codex 对照，或者一个专攻 URL 特征、一个专攻参数），每条路线用一个 git worktree 和单独的分支，晋级时由人合并。注意 dev 评估预算是所有路线共用的，并行越多消耗越快。
- 每轮的 `total_cost_usd` 记进日志。订阅账号受套餐用量限制，API 账号按金额计。
- Codex 可以共用同一份 `program.md`（作为它的 `AGENTS.md`）。它的沙箱与审批配置要另行查证，本方案没有覆盖。
- 以下几点文档没有写明，P1 时要实测：复合命令（如 `run.py ...; cat ...`）能否绕过允许清单；`-p` 模式下自定义 Stop 钩子是否生效；`dontAsk` 模式下各项拒绝是否如预期。

配置草图见附录 C。

## 5. 标签工厂（外环）

### 5.1 判官流水线

按 `权威度偏序标注prompt设计.md` 执行：两种顺序各判一次，不一致的剔除；带域名、遮域名各一轮；相关性门槛；保存分维度原始 JSON；temperature 0；模型版本与 prompt 版本写进文件名。**判官的模型或 prompt 一变，所有切分重新打标签、重新跑基线**，新旧批次的指标不能直接比。

### 5.2 两类抽样，严格分开

- **随机抽样**：真实引擎 top20 头尾抽对，外加 21 到 50 名辅助集。只有这类进 dev、holdout 和人工复核集，保证指标无偏。
- **定向抽样**（主动学习）：当前最好版本和基线判法不一致的对、分差很小的对、错例集中的站点类型。信息量大，但有选择偏差，**只进 train**。

### 5.3 判官本身的迭代（可选的第四个循环）

如果人工复核发现判官和人的一致率偏低（比如低于 80%），可以像 DSPy 的 GEPA 那样，用人工标签自动改进判官 prompt。但要和内环错开：判官改了，标签就变了，内环必须重来。

## 7. 风险与对策

| 风险 | 表现 | 对策 |
| --- | --- | --- |
| dev 过拟合 | dev 一路上涨，holdout 不动 | 门槛 ε、holdout 晋级、验证集按次数轮换、新站子集指标 |
| 对着判官刷分 | 带域名一轮涨、遮域名一轮跌；人工复核集不涨 | 遮域名护栏；发布前看人工复核集；定期抽查翻转样例 |
| 记站点 | 新增大量域名字面量；新站子集不涨 | 静态检查限额；按 query 切分；人工审阅 |
| 改评估作弊 | agent 修改 harness 或结果文件 | 权限拒绝、钩子拦截；`run.py` 执行提交与回退；打分进程看不到标签 |
| 不能上线 | 用了线上没有的字段或复杂逻辑 | 字段与模块白名单、复杂度预算、晋级时附移植说明 |
| 信号天花板 | 跑一段时间后再也没有提升 | 正常现象，说明现有 8 个字段已被榨干；转去外环补信号（标题、正文、ICP、站点级大模型评级） |
| 原地打转 | 反复尝试同类想法 | `journal.md` 与 `results.tsv` 每轮都给 agent；`ideas.md` 标注已试过的 |
| 学到判官的偏好 | 正文长度、品牌类特征的权重一路上升 | 按特征类别报告贡献；遮域名护栏；人工复核集；必要时用两个不同判官，两者都认为变好才算 |
| 跨轮次泄漏 | 后面的运行"提前知道"哪些对难 | 每晚全新克隆；审计记忆与 journal；失败信息不回显标签 |
| 成本失控 | 无人值守时 token 消耗过高 | 每晚设迭代上限和预算上限；驱动器在连续 N 次没有保留时提前停 |

## 附录 A：`program.md` 草稿

下面是给 agent 的指令初稿。P2 有人值守试跑时会据实际表现反复修改，这正是 Karpathy 说的"人在迭代 program.md，agent 在迭代代码"。

```markdown
# npv autoresearch：研究指令

## 目标
提高 dev 严格一致率（带域名一轮标签），越高越好；护栏指标不能变差。

## 你能改什么
- 只能改 sandbox/ 下的文件：features.py、config.json、lists/*.txt。
- 其他文件一律只读。dev 标签只能通过 run.py 拿到汇总数字；holdout 不在本仓库。
- 不要自己执行 git。提交和回退由 run.py 完成。

## 规矩
1. features.py 只能导入 math、re、urllib.parse；只能读 x 的 8 个字段、scorer 的站点表和 lists/。
2. 不要为了修某几对标签，写死在错例里看到的具体 URL 或域名。名单必须按通用标准整理
   （例如"以用户生成内容为主的平台"），并把标准写进 journal.md。
3. 不要改任何数值。新特征的权重和其他参数交给拟合：在 config.json 的 "fit" 列表里加特征名或参数名。
4. 一次只验证一个假设，改动要小，结果要能解释。
5. 简洁原则：指标持平但代码更简单，算成功；涨幅很小却多了一大块代码，不值得。
```

## 附录 B：`harness/run.py` 的约定

agent 做评估只能走这一个命令（另一条允许的命令 `errors.py` 只看 train 错例）。它是冻结的，只接受 `--hypothesis` 和 `--desc` 两个参数，传其他参数直接报错，这样 agent 没法把它指向别的标签文件。内部按顺序执行：

0. 把 `--hypothesis` 与 `--desc` 连同当前 diff 的哈希先写进 `results.tsv`，状态记为 pending。之后只追加结果，不改这一行。
1. `lint.py`：静态检查 sandbox 和 `journal.md`。不通过：回退，状态记为 lint_fail。
2. `score.py`（子进程）：在 train 上拟合 `fit` 列表里的权重，然后给快照全量打分。这个进程的工作目录和导入路径里都没有 `labels/`。超时 120 秒。
3. `evaluate.py`（子进程，不导入 sandbox 代码）：在 train 和 dev 上算严格一致率与全部护栏，按 query 聚类自助法算配对差的标准误，并检查无标签全量样本的分布漂移。
4. `gate.py`：与当前最好的提交比较，判定 keep、discard 或 review（需人工审阅，比如域名字面量超限）。
5. 执行 `git commit` 或 `git reset --hard`，往 `results.tsv` 追加结果。
6. 打印一行摘要。任何输出，包括报错信息，都不回显 dev 的逐对内容。保留时给精确数字：

```
status=keep     dev_acc=0.8164(+0.0041, 门槛 0.0032)  hard=0.6620(+0.0040)  blind=0.7710(+0.0010)  new_site=0.7930(+0.0020)  buried=0.081  complexity=23(+2)  dev_budget=187/300
```

不保留时，dev 只给粗档（4.2 节的 Ladder 规则），护栏只说哪一项没过：

```
status=discard  dev=持平  guard_fail=blind  complexity=25(+2)  dev_budget=188/300
```

`results.tsv` 的列：`time commit status hypothesis desc dev_acc dev_delta threshold hard_acc blind_acc new_site_acc buried_good_rate top_bad_rate score_ties missing complexity dev_budget_used`。agent 能读到的 `results.tsv` 里，discard 行的 dev 数字同样只写粗档。
