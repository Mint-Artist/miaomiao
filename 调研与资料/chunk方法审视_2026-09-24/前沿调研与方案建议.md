# Chunk 切分前沿调研与现有方案审视

核查日期：2026-09-24。对象：中文多类型网页、固定 embedding、混合搜索链路、页面 top10 GSB，以及业务方按序拼回正文的接口。

本次重新查询了论文原文、会议官网、产品官方文档和官方源码，补充了 2026 年研究；未运行外部方法基准。下文区分公开事实、证据局限和针对本项目的工程建议。本文不修改现有代码或将建议写成已确认决策。

## 1. 建议结论

**保留“简版 HTML 固定输入 → 结构解析 → 可替换切分策略”的主线。以结构感知、按类型保护作为有竞争力的起点，同时保留简单基线；不要预设它是最优方案。** 工业框架支持这种分层，而比较研究并未证明复杂语义方法普遍优于简单方法。[Docling][I03]、[NAACL 2025][P01]。

建议实施前调整五处：

1. **澄清数据契约**：简版 HTML 仍是固定产物；正文 T 和位置映射由统一解析层派生，不要求上游另交一套正文标准。
2. **区分正文交付与检索视图**：严格拼回约束保留在完整、有序、不重叠的正文块上；未来的重叠窗口、父子节点和生成式索引不要混进这份列表。
3. **LLM 上下文提前进入实验**：用户已有能力，适合与结构标题前缀同轮比较；不要因“语义切分收益不稳定”就推断上下文增强无效。
4. **保护策略是候选，不是信条**：类型、预算和上下文分别控制；标题绑定、提示框保护、表格行表示都需要坏例和指标验证。
5. **页面排序是主目标**：GSB 继续终审；补切分、chunk 召回与页面聚合诊断。完整答案生成不是本轮搜索选型的必要前置。

这些是根据证据和业务约束作出的建议，不是已经在真实 query 上测得的收益。

## 2. 先分清“chunk 方法”改变了哪件事

| 维度 | 典型方案 | 解决的问题 |
|---|---|---|
| 边界 | 固定窗口、句界递归、DOM/标题边界、句向量距离、LLM 边界 | 在哪里断开 |
| 检索表示 | 标题/表头前缀、LLM 上下文、字段键值化、命题 | 孤立片段能否被识别、检索 |
| 编码方式 | 独立 embed、Late Chunking、上下文专用训练 | 向量是否理解整篇背景 |
| 粒度与返回 | 小块召回、父子扩展、层级合并、query 自适应 | 索引多细、排序/返回看多大范围 |

同一个系统可以同时采用结构边界、上下文前缀和父子返回。因此不能把它们简单排成“传统→语义→LLM”的先进程度序列。这张分类表是本报告的工程归纳。

特别注意：LangChain 的 `HTMLSemanticPreservingSplitter` 是结构元素保护，并不因为名字中有 semantic 就等于逐句计算 embedding 距离。[官方源码][I04]

## 3. 业界：能核实的公开做法

产品文档证明的是“存在这种能力与设计”，不是对你们数据的效果保证，更不是同公司通用 Web 搜索内部算法的披露。

| 公司/框架 | 官方证据 | 对我们有用的部分 | 不能直接照搬的部分 |
|---|---|---|---|
| Google Cloud Agent Search | HTML layout parser 识别标题、段落、表格、列表等；可配置祖先标题及 chunk token 大小 | 结构保留与标题上下文有明确产品先例 | 产品 token 配置不是 256 中文字符；不是 Google Search 内部切分说明。[I01][I01] |
| Unstructured | 先 partition 成元素，再 chunk；同时提供 `new_after_n_chars` 软目标、`max_characters` 硬上限与原元素来源 | 最接近我们“结构单元+目标/上限+可回溯”的组合 | 它的软目标允许装箱越过目标后才停止，与我们“主要允许单个保护单元超目标”不完全相同。[I02][I02] |
| Docling | 原生文档对象上进行层级切分、token 拆分与合并；`contextualize()` 独立生成增强表示；支持重复表头 | 解析、边界、表示分层；表格路径单独处理 | 特定溢出配置可以省略表头，我们需自行决定是否允许失去列上下文。[I03][I03] |
| LangChain | HTML 标题切分和元素保护；保护指定元素时允许超过 `max_chunk_size` | 支持“完整性有时比目标长度更重要”的工程选择 | 不应默认保护整张长表；也不保证符合我们的严格拼回约束。[I04][I04] |
| AWS Bedrock | 固定、层级、语义策略并存；层级方式先召回子块，再用父块替换 | 索引粒度与返回粒度可以分开 | 父块替换后结果数可能减少；父子返回不能按相同 top-k 直接与平铺块比较。[I05][I05] |
| Anthropic | 为 chunk 生成简短上下文，再用于 embedding 与 BM25 | 与用户现有 LLM 上下文能力直接对应，且与边界算法相互独立 | 官方报告的是其评测的 top20 检索失败率，不能等同于页面 GSB。[I06][I06] |
| Chroma | 用原文相关 token 集合评估切分的召回、精度及 IoU | 证据坐标应独立于具体 chunk ID | 字符/token 重合是诊断，不能独自判断是否保全条件、否定或事实。[I07][I07] |

Anthropic 的具体结果值得正确解读：上下文 embedding + BM25 将其 top20 失败率从 5.7% 降到 2.9%，约为 **49% 相对下降、2.8 个百分点绝对下降**；加入 reranking 是另一个组合。它同时改变两条召回分支的输入，不能拿这个数字承诺“只加标题”或“只改向量”的收益。[官方方法及评测口径][I06]

## 4. 学术界：主要路线、近期进展及适用边界

### 4.1 简单基线与跨任务复核

**Is Semantic Chunking Worth the Computational Cost?（Findings NAACL 2025）**分别研究文档检索、证据检索和回答生成，发现所测语义切分的额外成本没有带来一致收益。它支持保留固定/递归基线，不证明所有语义方法无效，更不能直接否定 LLM 上下文前缀。[论文][P01]

**Beyond Chunk-Then-Embed（2026，本文按已核实的 arXiv 版本引用）**同时比较边界和编码顺序。在其六个 BEIR 数据集、四个 embedding 模型的比较中，简单结构类方法更适合语料库内检索，LumberChunker 更适合单文档定位。页面级使用 MaxP 聚合、评 nDCG@10；任务与我们接近，但没有覆盖中文亿级混合搜索。这里的“结构”包含句子/段落/固定块，不能直接解读为 DOM 方案胜出。[原文 §3–4][P02]

已有本地材料将该文标作 SIGIR 2026。本次公开原文仍含匿名审稿占位信息，未获得独立会议记录确认，故本报告不把会议归属作为证据；也不据此断言它未被接收。

### 4.2 LLM 边界与层级构建

**AutoChunker（ACL Industry 2025）**通过 LLM 组织结构化文本，并把检索结果扩展成子树、去除重叠；还提出完整性、噪声、上下文连贯性等质量诊断。借鉴点是层级关系和诊断，不是强迫所有元素独立成为固定大小的向量块。[原文 §3.3–4][P03]

**MoC（ACL 2025）**使用粒度感知的 chunking learners，让模型生成用于从原文抽取块的结构化正则表达式，并引入 Boundary Clarity/Chunk Stickiness。对我们更值得借鉴的是“模型提出边界、程序从原文取片”，而不是让模型重新输出整篇正文；其内在指标不能替代页面相关性。[论文][P05]

**HiChunk（ACL 2026）**结合学习式层级结构和检索时 Auto-Merge，并以证据密集的 HiCBench 暴露简单 QA 集不容易看出的切分问题。其合并检查子节点覆盖及返回 token 预算，实验也比较相同返回预算。适合借鉴层级和敏感诊断集；是否需要训练层级模型要看已有 HTML 结构质量。[论文及 §5.6][P04]

### 4.3 上下文进入向量，而不一定进入文字

**Late Chunking（2024 起）**先对长文生成上下文化 token 表示，再按 chunk 范围池化。它仍需边界，改变的是编码顺序；不是“把整篇的一个向量切成多个”。需要长上下文模型、token 表示和合适的 pooling 接口，仅有普通 embedding 服务未必能实现。[原论文][P07]

**Context is Gold / ConTEB / InSeNT（EMNLP 2025）**研究上下文依赖的检索评测和专门训练，结合 late pooling 改善表示。这说明上下文收益还受模型训练影响。用户当前固定 embedding，因此可借鉴诊断设计；换模型/后训练应归到另一个实验轴。[论文][P08]

### 4.4 改变检索单元或动态选择粒度

**Dense X Retrieval（EMNLP 2024）**将命题作为自包含检索单元，说明索引粒度会影响检索与 QA。但命题通常是生成或改写表示，不能直接当作原文片段拼回；在我们系统中应是带来源的辅助索引。[论文][P10]

**SmartChunk Retrieval（ICLR 2026）**用 query-aware planner 选择抽象层级，并通过轻量压缩生成高层表示；评测涵盖五个 QA benchmark 和一个域外数据集。它代表“查询时选择粒度”的近期方向。我们可以先试规则式父子扩展，再决定是否值得训练 planner；不能将长文 QA 优势直接推广成网页 GSB 优势。[会议官方论文页][P09]

### 4.5 HTML、表格及 2026 年新证据

**HtmlRAG（2025 修订版）**保留 HTML，清理并通过块树剪枝组织已检索网页知识。它支持保留 HTML 结构信息，但主要解决检索后的知识表示与压缩，不能证明某一种离线索引边界最好。[论文][P06]

**Structure-Aware Chunking for Tabular Data（2026-05 预印本）**以行树、键值块和预算约束维护行内关系。值得测试“行+列名”表示。其 MAUD 实验使用合同名与问题标签的启发式匹配作为相关性判定，不能把所报大幅提升直接推广到真实网页查询。[方法与评测 §V-B][P12]

**Structure-Aware Semantic Chunking with Title-Chain Prefixes（2026-08 预印本）**组合标题切分、语义合并和标题链。作者报告前缀有无会显著影响评委一致性，但研究只有一个私有知识库/embedding，未做逐阶段消融，也未人工审计成功运行。可据此警惕“评委看到了不同信息”，不能把联合收益归因于标题一项。[原文 Limitations][P11]

**Evaluating Chunking Strategies on Academic Texts（2026-07 预印本）**在所测学术长文场景中未发现聚类切分优于简单策略，并报告 RAGAs faithfulness 的可靠性限制。作为补充反例，不是跨领域定论。[作者论文][P13]

因此，本次并没有找到足以支持“统一改用最前沿语义/LLM 切分就会更好”的证据。较稳妥的实验方向是：结构约束、上下文表示、多粒度分别可替换，保留简单参照。

## 5. 审视我们的现有设计

以下为项目建议，外部方法只提供参考；没有用它们替代本项目的验证。

### 5.1 应保留的部分

- **简版 HTML 固定产物**：继续作为上游 EC 对齐接口。T 与 DOM/字符映射是可重建的派生结果，可以缓存，不必要求另外落库。
- **正文与增强文本分离**：标题、metadata、表头源文字保留，重复前缀只用于检索表示。
- **目标预算+类型保护+绝对上限**：符合工程框架中的可行模式；256 是起点，不是研究结论。
- **表格单独处理**：连续行分组合理，不能只把整张表保护成巨块。
- **版本、配置和来源可回溯**：便于比较方法和交付胜出版本。

### 5.2 最重要的补充：正文块不必承担所有索引形式

当前 `join(chunk.text) == T` 是有效且已确认的业务契约。但如果将它要求于未来的每一种索引记录，就无法自然表达重叠窗口、多层父子块或生成命题。

建议在概念上区分三个视图，首版不必都落库：

```text
固定简版 HTML H
  └─ 统一解析：正文 T + 结构/范围映射 M
       ├─ 完整正文块：连续、不重叠，join(text) == T（交给拼接业务方）
       └─ 检索视图：正文块或来源范围 → 检索文本/向量 → doc_id
                      └─ 命中后可选扩展邻块/父节点供排序或证据返回
```

首版检索视图与正文块可以一一对应；未来扩展时用 `source_spans`/结构 ID 关联，不把额外索引记录加入“拼回正文”的列表。生成内容的来源映射只能表示依据，不能自动证明每个生成事实忠实。

这保留原合同，不需要为了追求前沿而立即建设复杂多索引系统。借鉴来源是 Docling 的正文/增强序列化区分，以及 Bedrock、AutoChunker、Dense X 的不同粒度设计。[I03][I03]、[I05][I05]、[P03][P03]、[P10][P10]

### 5.3 类型保护还需防止错误的“完整性”假设

- 一个 `<p>` 可能包含多个主题；一个 `<div.note>` 也可能是模板误标的大容器。保护依据应包含结构可信度与长度，而不只是标签名字。
- “标题随首段”是默认偏好，不能压过正文顺序和模型上限；首标题前后夹 metadata 的例外已经在规格中记录，应保留。
- 除 max/p95 长度外，记录类型、超目标原因、完整性/噪声诊断和检索表现。三页样本不足以确认超长段落概率。
- H 要看实际 tokenizer、特殊 token、提示前缀及 truncation 行为；不能简单采用某云产品的默认 token 大小，也不能假设字符数等于 token 数。

### 5.4 表格不仅需要正确边界，还需要可检索表示

原文 T 中的 TAB/LF 表示可保持确定性，但不能预设这种写法对 embedding 最好。建议独立比较：

1. 紧凑行文本 + 一份表头；
2. 每行字段键值化，例如“学校名：清华大学；专业组：004组；2025分数：688；2025位次：85”；
3. 保留小片段 HTML/Markdown 表结构。

这些都只改变检索视图，原文交付不变。比较需要把重复列名消耗的 token、行覆盖及实际召回一并记录。复杂 rowspan、多个表头、单位与脚注也应进诊断集，不能只验“171 行都在”。该实验动机参考表格结构研究，而具体格式是否更好须在本地判断。[P12][P12]

### 5.5 标题路径、metadata、LLM 上下文不能一次性混为一项

建议先比较无前缀、结构前缀、结构前缀+现有 LLM 上下文。产品/版本等 metadata 可能非常关键，时间/阅读量可能是噪声；保留全部正文不等于要重复注入全部 metadata。

“所有祖先标题”与“文档标题+最近章节”应作为可选配置，不能先验认定从最深层开始删除一定最好。LLM 若改写关键条件、版本或否定，即使召回提高也需单独标记错误。

需要区分两种比较：

- **表示消融**：正文边界固定，只改增强表示，确保不超模型限制，同时报告实际输入长度变化。
- **可上线组合**：固定总预算规则，允许前缀占预算从而改变装箱。它测整个组合，不能声称只测了前缀。

### 5.6 补页面聚合这一层，否则诊断不完整

搜索返回的是网页。chunk 变多后，一个页面进入候选池的机会和重复命中也会变，原始 top-k chunk 提升不等于 top10 网页提升。

首轮冻结生产的 chunk→page 聚合、去重、融合和 reranker 配置，记录不同阶段的页面 Recall、每页块数和每页候选命中数。需要时再单独比较 MaxP、top-m 聚合等策略，不把它们混入边界实验。

纯粹扩大返回父块若不进入页面打分/重排，只会改变证据文本，未必改变网页排序；因此父子扩展的优先级取决于你们实际链路消费哪里，而不是因为某 RAG 论文取得了更好答案。

## 6. 建议的实验顺序

### 6.1 第一轮候选

| ID | 候选 | 主要回答的问题 |
|---|---|---|
| P0 | 用户生产代码+真实配置+生产正文 | 当前系统是什么水平 |
| L0 | 当前 256 硬上限原型，原样冻结 | 新代码是否引入历史回归；单独标记它的正文缺项 |
| R1 | 同一 T 的句界/递归装箱，硬预算，无增强 | 简单且完整的可比基线 |
| R2 | 同一 T 的结构边界，硬预算，无增强 | R1→R2：边界利用结构是否有收益 |
| R3 | R2 改为类型保护、目标 B+上限 H | R2→R3：保护是否值得额外长度 |
| C1 | 结构候选+标题/表头前缀 | 上下文表示是否有效 |
| C2 | C1+用户已有 LLM 上下文 | 已有能力是否带来增量 |
| S1 | 同一 T、章节内句向量边界，匹配上下文配置 | 结构基础上语义断点是否值得 |

R1/R2 的纯比较可关闭全部增强，但表格需另报告，并补带相同表头策略的结构/句界对照，避免由“没有列名”决定全部输赢。C1/C2 同时按上一节区分表示消融与实际预算组合。

不必一开始跑所有交叉组合；开发集先做主对照，再补“预算×上下文”等有理由的交互。建议每类主要方法都有至少两三个合理预算档，例如 256/384/512 字符，前提是符合模型实际限制；这些数值是候选搜索网格，不是生产上限，也不是论文统一标准。

### 6.2 第二轮

- **表格序列化对比**：优先级高，因为当前已有真实表格页。
- **父子/邻块扩展**：若排序/证据侧确实消费上下文，优先试规则版；否则作为下游证据实验。
- **LLM 边界或层级重建**：优先用于标题缺失、结构混乱页；让模型给边界/节点关系，程序执行原文切片。
- **Late Chunking**：先核查固定 embedding 是否允许合适的 token 表示、长窗口及 pooling；若必须更换模型，单列模型实验，不能标成“只改切分”。
- **SmartChunk 式学习 planner、命题索引、多模态切分**：保留接口，等基础评测揭示具体瓶颈后再投入。此次不建议直接替换整个生产路线。

## 7. 评测设计：以搜索为主，诊断补充

| 层次 | 主要检查 | 定位用途 |
|---|---|---|
| 数据契约 | 严格拼回、范围、资源、表格行列关系、输入版本 | 排除内容缺失/重复和解析错误 |
| 内在质量 | 主题混杂、条件完整、标题/主体消歧、段落/步骤断裂 | 判断结构保护是否真正有用 |
| Chunk 召回 | 证据覆盖与事实/条件支持分开；固定 K 与固定返回预算双视角 | 区分“证据没被放在一起”和“有证据却没召回” |
| 页面排序 | 页面 Recall、nDCG@10；阶段性候选与重复率 | 观察 chunk→page、融合、重排造成的变化 |
| 最终业务 | 固定 query 的 top10 页面 GSB | 决定是否替换生产方案 |

固定 token 返回预算特别适合证据/扩展比较；不能拿它替换网页 GSB 的真实运行条件。页面实验应固定实际候选、延迟和排序配置，并同时记录索引规模与输入量。

### 数据与标注

- 同时建立真实流量集与切分敏感诊断集。后者覆盖型号/版本、前置条件、多步骤、表格列名与单位、跨段证据等；分别报告，不用偏结构的诊断分布冒充整体流量收益。
- 日志最终推荐 URL 是弱标签，不是人工真值；旧系统未推荐的网页也可能相关。新旧方法候选合并后再评审，避免只奖励复现旧系统。
- 日志 top50 可用于开发和诊断，但单独在它们之间竞争会低估全库检索难度；正式 GSB 使用可比的冻结背景。若只更新一部分网页，应明确称局部更新实验，不宣称全库重切收益。
- 标注落在稳定源文本/事实条件上，不直接标某方法生成的 chunk ID。页面相关性评委看到相同规范的源页面信息；另用独立任务评判检索 chunk 自身是否足够，避免两类标签混用。
- LLM 评审可作为主力，但仍需小规模人工校准、盲化方法名、随机顺序、固定模型/prompt，并报告分歧。不能以“大模型额度充足”替代可靠性检验。
- 用开发集调参，保留锁定测试集；按 query 配对比较和估计区间，预先约定晋级规则。近重复网页、模板与时间泄漏需在抽样时处理。

### 成本与公平性

算力充足也应报告每页向量数、embedding token、索引体积、构建/更新耗时、检索/重排延迟和截断率。这些既是部署成本，也是比较中的混杂因素。

同一个最大长度不意味着平均长度、总索引量、top-k 正文量相同。建议同时报告真实部署效果和近似资源匹配的诊断结果，而不是强迫所有方案每页生成相同数量的块。

## 8. 对当前规格的具体处理建议

审视对象：[正文契约与切分规则 vNext](../../chunk流水线/规格/vNext/正文契约与切分规则.md)。

| 当前内容 | 建议 |
|---|---|
| 简版 HTML → T/映射 | 明确 T/映射是统一解析层的派生产物；无需新增上游交付要求 |
| 全 chunk 按序拼回 | 明确指正文交付集合；未来辅助检索记录分开管理 |
| 256 目标、类型保护、H 待定 | 保留为候选；补同正文硬预算和多预算档，不预设保护必胜 |
| 标题随下文、metadata 可实验 | 保留，补结构可信度与例外统计 |
| TAB/LF 表格正文 | 可保留为还原格式，检索序列化另行实验 |
| LLM 上下文预留 | 调整为首轮候选，复用已有能力 |
| parent_id/prev/next | 保留续块和邻接语义；另留章节/表格节点关系，避免一字段多义 |
| 搜索实验 | 明确生产页面聚合、两条混合召回分支的字段和后续排序条件 |

最先实现的仍然可以是轻量统一解析层与严格还原检查；但在写切分器之前，把“正文交付集合”和“可扩展的检索表示”界线写清楚。不要为了基础设施完整而推迟真实 query、生产基线和输入长度限制的收集，两条工作应并行推进。
