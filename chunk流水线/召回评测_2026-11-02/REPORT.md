# 结构保护切分的向量召回评测报告

> 评测日期：2026-11-04　｜　代码：本目录 `recall_pipeline.py`、`embed_job.py`、`diagnostics.py`

## 摘要

- **结论**：基于 HTML 结构的切分在向量召回上全面优于现有基于 content 的切分。建议 EC 补全 html 字段，保证所有网页都输出保留结构标签的正文 HTML。
- **效果**：在 html 字段完整的网页上，相比现有方案：
  - 相同精排输入字数下，召回提升 **2.1～2.7 个点**；
  - 前 10 个网页的召回提升 **0.5～1.4 个点**。
  - 这些提升除表格网页的前 10 网页召回外均显著，95% 置信区间不含 0。
- **收益来自结构**：与块长相近的 markdown 结构切分相比，html 的优势随网页结构丰富程度递增。相同字数下：
  - 纯文本网页 +0.6；
  - 标题列表网页 +1.3；
  - 表格网页 +2.1。
- **当前阻碍**：全库约 **21%** 的网页 html 字段为空，content 为空的只有 7%。在标准答案网页里，约 12% 的网页 EC 已经抽出了正文，却没有输出 html。这是 html 方案整体反而落后于现有方案的主要原因，已确认是数据缺失，不是解析问题。
- **过渡方案**：html 补全之前，可以用 markdown 结构切分。它的网页级召回与现有方案持平，相同字数下召回显著更高（+2.3～+3.5，不随标准答案的严格程度改变）。
- **结论偏保守**：标准答案来自线上精排结果，而线上精排基于现有的 content 切分，因此标准答案偏向现有方案。在这种情况下，结构切分仍然显著胜出。

## 1. 背景与目标

线上现在把 EC 抽取的 `content` 字段按 `<br>` 分段，再打包到约 256 字切成 chunk，不感知标题、表格、列表等结构。这样会产生几类问题：

- 标题和正文被切开；
- 表格被切成没有表头的碎片；
- 一个 chunk 跨越多个章节。

本次评测要回答三个问题：

1. 保护结构的切分方式，能否提升向量召回？
2. 提升是来自"结构被保护"，还是仅仅因为块更短？
3. 结构信息应该从 EC 的哪个字段获取：`markdown` 还是 `html`？

## 2. 评测设计

### 2.1 切分方法

| 方法 | 输入字段 | 做法 |
|---|---|---|
| `content_br`（基线） | `content` | 线上现有切分：按 `<br>` 分段，打包到约 256 字 |
| `md_struct` | `markdown` | 结构切分 |
| `html_struct` | `html` | 结构切分，结构从 HTML 标签解析 |

两种结构切分的规则相同：

- 遇到标题就断开，标题与紧随的第一段放在同一块；
- 不跨章节，同一节内的同类内容（正文段落、列表项、同一张表的行）合并到软上限 256 字；
- 不超过 512 字的段落不拆，超过的按句切开；
- 表格按行打包，每一块都带上表头；
- 正文少于 20 字的块丢弃。

三种方法使用同一个向量模型、相同的前缀和截断长度（512 token），向量以 fp16 存储并做 L2 归一化。

### 2.2 语料

| 项目 | 数值 |
|---|---|
| 网页总数 | 3,462,435：随机优质网页库，加上评测 query 在线上召回到的相关网页（补入时按 url 去重，跳过 12,576 条重复） |
| 向量数 | content_br 19,505,949；md_struct 26,882,312；html_struct 23,632,783 |
| 全库平均块长 | content_br 228.9 字；md_struct 169.6 字；html_struct 182.4 字 |
| 切不出块的网页 | content_br 241,267（7.0%）；md_struct 245,534（7.1%）；**html_struct 735,558（21.2%）** |

把 query 相关的网页补入随机库，目的是保证标准答案网页都在库里，同时让随机网页充当干扰项，使检索难度接近线上。

### 2.3 Query 与标准答案

- **query**：3377 条线上 query，使用线上检索时的原文。
- **标准答案**：每条 query 在线上链路中精排 top-10 的网页，共 31,224 个，平均每条 query 9.2 个；全部都在库里。
- **评测粒度**：网页级。一个 chunk 命中标准答案网页，就算命中。网页级标注和切分方式无关，因此不同切分方法可以直接比较。
- **偏差说明**：线上精排基于现有的 content 切分做召回和排序，所以这份标准答案天然偏向基线 `content_br`。诊断 4 用更严格的标准答案验证了结论的稳健性。

### 2.4 检索与指标

- **检索方式**：对每条 query 做 GPU 精确暴力检索，取 top-100 个 chunk，不使用近似索引，避免近似误差混进方法之间的比较。
- **主要指标**：

| 指标 | 含义 |
|---|---|
| `hit@K` / `recall@K` | 前 K 个 **chunk** 里是否命中、覆盖了多少比例的标准答案网页 |
| `MRR` | 第一个命中标准答案的 chunk 排名的倒数 |
| **`hit@3000字`** | 从第 1 名起累加 chunk 字数，3000 字以内是否命中。按送进精排的字数截断，**用于抵消块长不同的影响**，是比较不同切分方法的主要指标 |
| 网页 recall@N | 检索结果按网页去重后，前 N 个网页覆盖了多少比例的标准答案 |
| `nDCG@10` | 按网页去重后前 10 个网页的排序质量 |

- **显著性**：每种方法与基线在同一批 query 上逐条配对，用 bootstrap（2000 次）估计差值的 95% 置信区间。置信区间不含 0 才算显著。下文写作 `Δ+2.9 [+1.7, +4.1]`，单位是百分点。

## 3. 总体结果

| 方法 | MRR | hit@1 | hit@10 | hit@100 | recall@100 | hit@3000字 | nDCG@10 |
|---|---|---|---|---|---|---|---|
| content_br | 0.3220 | 0.1682 | 0.6657 | 0.9805 | 0.5212 | 0.7142 | 0.1494 |
| md_struct | 0.3195 | 0.1682 | 0.6583 | 0.9760 | 0.5071 | 0.7433 | 0.1471 |
| html_struct | 0.3097 | 0.1620 | 0.6509 | 0.9745 | 0.4686 | 0.7270 | 0.1403 |

相对基线的差值：

| 方法 | ΔMRR | Δhit@10 | Δrecall@100 | Δhit@3000字 |
|---|---|---|---|---|
| md_struct | −0.3 [−1.2, +0.6] | −0.7 [−2.0, +0.5] | −1.4 [−1.8, −1.1] | **+2.9 [+1.7, +4.1]** |
| html_struct | −1.2 [−2.3, −0.3] | −1.5 [−2.9, +0.0] | −5.3 [−5.7, −4.8] | +1.3 [−0.1, +2.6] |

只看总表，会得出两个结论：

- md_struct 的头部结果与基线持平，相同字数下显著更好；
- html_struct 整体偏差。

接下来的诊断说明：md_struct 在 recall@100 上的下降来自块更短；html_struct 偏差则来自 html 字段的数据缺失。

## 4. 诊断

### 4.1 按网页去重后，md_struct 与基线持平（诊断 1）

| 方法 | top-100 块里的不同网页数 | 网页 recall@1 | @5 | @10 | @20 |
|---|---|---|---|---|---|
| content_br | 66.97 | 0.0184 | 0.0820 | 0.1463 | 0.2470 |
| md_struct | 65.66 | 0.0187 | 0.0808 | 0.1433 | 0.2435 |
| html_struct | 64.43 | 0.0181 | 0.0762 | 0.1369 | 0.2312 |

- md_struct 的网页级召回与基线只差 0.3 个点左右，top-100 个 chunk 里的不同网页数也只少了 1.3 个。
- recall@100 下降，原因有两个：块更短，100 个 chunk 能装下的字数就更少；一个网页也更容易占掉多个名额。这不是因为 md_struct 漏掉了网页。

### 4.2 html_struct 的问题是丢了网页（诊断 2、6）

标准答案网页的切分情况：

| 方法 | 块数/页 均值 | 块数/页 中位数 | **切不出块的网页占比** | 正文字数/页 中位数 | 平均块长 |
|---|---|---|---|---|---|
| content_br | 7.21 | 5 | 1.2% | 932 | 220.2 |
| md_struct | 9.30 | 6 | 1.2% | 954 | 174.2 |
| html_struct | 8.05 | 5 | **13.1%** | 852 | 183.8 |

在 4094 个 html 切不出块的标准答案网页中：

| html 字段 | 网页数 |
|---|---|
| 为空 | 4035（98.6%） |
| 很短（< 200 字符） | 52 |
| 有内容 | 7 |

抽查"有内容"和"很短"的几条，都是反爬拦截页或者只有导航文字的页面，本来就没有正文。所以解析代码没有问题，**是 EC 的 html 字段缺失**。content 切不出块的只有 1.2%，两者之差说明：约 12% 的标准答案网页，EC 抽出了正文，却没有输出 html。

### 4.3 结论不随标准答案的严格程度改变（诊断 4）

只取精排前 3 或前 5 名当标准答案，重新计算：

| 标准答案 | md_struct Δhit@3000字 | md_struct Δhit@10 | html_struct Δhit@3000字 | html_struct Δhit@10 |
|---|---|---|---|---|
| 精排前 3 | **+2.3 [+1.0, +3.4]** | −1.2 [−2.4, −0.0] | +0.5 [−0.9, +1.8] | −2.4 [−3.8, −1.1] |
| 精排前 5 | **+3.5 [+2.2, +4.8]** | −1.0 [−2.3, +0.3] | +1.4 [−0.1, +2.8] | −2.3 [−3.7, −0.8] |
| 精排前 10 | **+2.9 [+1.7, +4.1]** | −0.7 [−2.0, +0.5] | +1.3 [−0.1, +2.6] | −1.5 [−2.9, +0.0] |

"相同字数下 md_struct 更准"在三种标准答案下都成立，不是标准答案里的弱相关网页造成的。两种方法的 hit@10 略低，因为 10 个 chunk 装下的字数比基线少。这里的 html 数字仍然包含 html 缺失的那部分网页。

### 4.4 按标准答案网页的结构类型分组（诊断 3、5）

网页类型按它的 markdown 判断：

- 有表格的算"表格"；
- 没有表格、但有 `#` 标题或列表的算"标题列表"；
- 其余算"纯文本"。

31,224 个标准答案网页中，纯文本 18,762 个，标题列表 10,333 个，表格 2,129 个。

诊断 3 按 query 分组：标准答案里只要有一个网页带结构，这条 query 就算"带结构"。每条 query 平均有 9.2 个标准答案网页，所以几乎所有 query 都会被归为"带结构"，纯文本组只剩 137 条，区分度不够。下面用诊断 5 的分法：**按每个标准答案网页自己的类型分组**，计算每条 query 中该类标准答案网页的召回比例，再按 query 配对比较。

相对基线的差值（包含 html 缺失的网页）：

| 网页类型 | md_struct：3000 字内召回 | 前 10 网页召回 | html_struct：3000 字内召回 | 前 10 网页召回 |
|---|---|---|---|---|
| 表格（1310 条 query） | +0.4 [−1.0, +1.9] | −1.3 [−2.7, +0.2] | **+2.4 [+1.0, +3.9]** | +0.4 [−1.1, +1.8] |
| 标题列表（3154 条） | **+1.5 [+0.8, +2.2]** | −0.3 [−0.9, +0.3] | **+2.4 [+1.7, +3.1]** | **+0.8 [+0.1, +1.4]** |
| 纯文本（3346 条） | **+1.2 [+0.8, +1.6]** | −0.1 [−0.5, +0.2] | −1.6 [−2.1, −1.1] | −2.1 [−2.6, −1.6] |

- **md_struct 在各类网页上的提升差不多**，纯文本网页上也有。所以它的收益主要来自块更短，不是结构保护。在表格网页上它几乎没有收益。
- **html_struct 在有结构的网页上提升最大**，只在纯文本网页上为负。html 为空的网页按 markdown 判断大多是纯文本，所以数据缺失的影响基本都落在了这一组。

### 4.5 排除 html 缺失后，html_struct 全面领先，并且结构越丰富优势越大（诊断 7）

只保留 html 能切出块的标准答案网页，排除 4094 个。三种方法都在同一批网页上比较，所以仍然是公平的配对比较。

**对比现有方案（content_br）：**

| 网页类型 | md_struct：3000 字内召回 | 前 10 网页召回 | html_struct：3000 字内召回 | 前 10 网页召回 |
|---|---|---|---|---|
| 表格（1309 条） | +0.4 [−1.1, +1.8] | −1.3 [−2.7, +0.1] | **+2.5 [+0.9, +4.0]** | +0.5 [−1.0, +2.0] |
| 标题列表（3143 条） | **+1.5 [+0.8, +2.2]** | −0.3 [−0.9, +0.4] | **+2.7 [+2.0, +3.5]** | **+1.1 [+0.5, +1.8]** |
| 纯文本（3301 条） | **+1.4 [+1.0, +1.9]** | +0.0 [−0.4, +0.5] | **+2.1 [+1.6, +2.6]** | **+1.4 [+0.9, +1.9]** |

**html_struct 对比 md_struct**（两者平均块长接近：183 字对 174 字，块长的影响基本抵消）：

| 网页类型 | 3000 字内召回 | 前 10 网页召回 |
|---|---|---|
| 表格 | **+2.1 [+1.1, +3.2]** | **+1.8 [+0.8, +2.8]** |
| 标题列表 | **+1.3 [+0.7, +1.8]** | **+1.4 [+0.9, +1.9]** |
| 纯文本 | **+0.6 [+0.3, +0.9]** | **+1.4 [+1.0, +1.7]** |

- **在两种口径下都提升。** md_struct 只在"按字数算"的口径下有提升，按"前 10 个网页"算时与基线持平。html_struct 在两种口径下都显著提升，也就是说它能把相关网页排得更靠前。
- **结构越丰富，html 对 md 的优势越大。** 按字数口径：纯文本 +0.6，标题列表 +1.3，表格 +2.1。这与"收益来自结构保护"的预期一致。
- **纯文本网页上 html 也领先**，可能有两个原因：
  - "纯文本"是按 markdown 判断的，有些网页在 markdown 里看不出结构，html 里却仍有 `<h>` 标签或加粗小标题。也就是说，EC 转 markdown 时丢了结构，这部分其实也属于结构带来的收益。
  - html 正文比 markdown 少了链接、图片地址这类语法噪声。

## 5. 结论与建议

### 5.1 结论

1. **结构保护有效，HTML 是更好的结构来源。** 在 html 字段完整的网页上，html 结构切分相比现有方案，相同字数下召回 +2.1～+2.7，前 10 网页召回 +0.5～+1.4。与块长相近的 markdown 结构切分相比，优势随结构丰富程度递增（+0.6 → +1.3 → +2.1）。
2. **markdown 结构切分是安全的过渡方案。** 网页级召回与现有方案持平，相同字数下召回 +2.3～+3.5，不随标准答案的严格程度改变。不过它的收益主要来自块更短，结构本身的贡献不明显，在表格网页上几乎没有收益。
3. **EC 的 html 字段目前不能直接用。** 全库 21.2% 的网页 html 为空，content 为空的只有 7.0%。这些网页在 html 方案里没有任何向量，导致 html 方案整体落后于现有方案。

### 5.2 对 EC 的变更请求

1. **补全 html 字段。** 对所有网页输出正文 HTML，覆盖率与 content 一致。至少要解决"已经抽出正文、却没有输出 html"的那部分网页：在标准答案网页中约占 12%。
2. **保留结构标签。** 正文 HTML 中保留 `<h1>`–`<h6>`、`<table>`（含 `<th>`）、`<ul>`/`<ol>`/`<li>`、`<p>`、`<pre>`。
3. **过渡期**：html 补全之前，或者对确实拿不到 html 的网页，用 markdown 字段做结构切分兜底。

## 6. 局限

1. **只评了向量召回这一环。** 精排、生成的效果没有评测。最终方案还需要端到端 GSB 确认。
2. **标准答案偏向现有方案，噪声也较大。** 网页 recall@10 只有约 0.15，hit@1 约 0.17，说明线上精排 top-10 与纯向量召回的重合度不高：线上可能还有其他召回通路，精排也会大幅调整排序。这些噪声会压缩方法之间的差距，所以本报告的提升幅度应当看作下限。
3. **网页类型按 markdown 自动判断**，没有人工标注。部分网页在 markdown 中丢失了结构，可能被误归为纯文本。
4. **索引规模会变大。** html 方案的向量数比现有方案多约 21%（html 补全后可能更多），markdown 方案多约 38%。存储和检索成本需要一并评估。
5. **只评了一种块长设置**（软上限 256、硬上限 512）。没有另做"块长与结构切分相同、但不保护结构"的对照方法。块长的影响是通过 `hit@3000字` 指标，以及 html 与 md 块长接近这一事实来控制的。

## 7. 复现

本目录下的文件：

| 文件 | 用途 |
|---|---|
| `recall_pipeline.py` | notebook 脚本（以 `# %%` 分段）：读取数据 → 切分 → 向量推理 → 检索 → 评测；支持分批入库（`PART_PREFIX`、`DEDUP_URLS`） |
| `embed_job.py`、`run_embed_job.sh` | 任务队列版的向量推理。一个任务推理一种切分方法，按分片断点续跑，产出与 notebook 逐字节一致 |
| `query_tools.py` | query 文件检查与清洗（去掉 NaN 或空的 url） |
| `diagnostics.py` | 本报告第 4 节的诊断 1–7。接在 notebook 第 14 段之后运行，直接使用检索结果，不重新检索 |
| `examples/` | query 文件格式样例 |

运行步骤：

1. 在 notebook 中运行第 1–9 段，切分随机网页库。
2. 改配置，再次运行第 1–7 段和第 9 段，补入 query 相关网页：`DATA_GLOB` 指向新数据，`PART_PREFIX = "inj-"`，`DEDUP_URLS = True`。
3. 每种方法提交一个任务队列任务：`bash run_embed_job.sh <方法名>`。
4. notebook 依次运行第 1–7、10、12、13、14 段，得到第 3 节的总体结果。
5. 在同一个 notebook 中运行 `diagnostics.py` 的诊断 1–7，得到第 4 节的诊断结果。
