# Gold 标注与离线评测规范

用于对比多种 chunk 切分方法(定长贪心 / 标题边界约束 / 语义切分)。
配套代码:`chunk_b1.py`;背景与结论见 `README.md`。

**核心原则:标注只做一次,在原文上标,与任何切分方案无关。** 之后所有方法用同一段程序打分,不再调 LLM。

---

## 第一部分 · 标注

### 1. 输入

只给两样:

- `query` —— 真实 click query
- 该 query 点击文档的**完整规范化正文**(`normalized_content`,含 `<br>`)

**铁律:不给任何 chunk。** 否则谁的 chunk 被拿去标注,谁就天然占便宜,整套比较失效。

同理:**绝不能拿 `clicked_chunk` 当标准答案** —— 它是线上现有切分方法的产物。

### 2. 输出字段

| 字段 | 含义 | 例 | 可空 |
|---|---|---|---|
| `answer` | 正文里直接回答 query 的**最小连续文字** | `3121` | ❌ 必填 |
| `required_context` | 不带上它答案会被认错的标签词(数组) | `["历史类"]` | ✅ **多数为空** |
| `trap_answer` | 正文里那个「长得像但错」的答案 | `29273` | ✅ |
| `alt_evidence` | 正文里是否还有另一处也能独立回答 | `true` | — |
| `confidence` | 自评 0~1 | `0.95` | — |

三个文本字段**必须是正文里的原样子串** —— 不改写、不跨句拼接、不补单位。

```json
{
  "query_id": "q_001",
  "query": "安徽历史类600分对应多少名",
  "doc_id": "doc_001",
  "answer": "3121",
  "required_context": ["历史类"],
  "trap_answer": "29273",
  "alt_evidence": true,
  "confidence": 0.95
}
```

### 3. Prompt

```
你会看到一个用户搜索词和一篇文章的完整正文。请判断这篇正文如何回答这个搜索词。

【搜索词】
{query}

【正文】
{normalized_content}

请只输出 JSON,字段如下:

answer            正文里直接回答搜索词的最小一段连续文字。必须是正文里的原样子串,
                  不要改写、不要合并多处、不要补充单位。正文回答不了就输出 null。

required_context  字符串数组。判断方法只有一句:正文里除了正确答案,是否还存在
                  另一个「长得像、但其实是错的」答案?如果有,列出区分两者所必需
                  的标签词(如「历史类」「2024年」「母公司」「鼻部整形」)。
                  如果答案在正文里只有一处、不可能认错,输出 []。
                  这一项多数情况下应该是 []。

trap_answer       上面那个「长得像但错」的答案,原样子串。没有则 null。

alt_evidence      正文里是否还存在另一处也能独立、完整回答这个搜索词。true/false。

confidence        0~1,你对以上判断的确信度。

不要输出任何解释。
```

`answer` 为 null → 该条作废(query 与文档不匹配)。

### 4. 「双胞胎」的常见形态

`required_context` 该不该填,只取决于一个问题:**正文里除了正确答案,还有没有另一个长得像但错的答案?**

| 正文里的并列 | `required_context` | 领域 |
|---|---|---|
| 物理类 / 历史类 | 科类 | 高考 |
| 眼部整形 / 鼻部整形 / 胸部整形 | 项目类别 | 医美价格表 |
| 2023年 / 2024年 同一指标 | 年份 | 财报 |
| 母公司 / 合并 | 报表主体 | 财报 |
| 北京 / 上海 | 城市 | 地域类 |

对应业界所说的难负例四种混淆型:时间混淆、实体混淆、粒度混淆、单位混淆。

### 5. 程序校验(不过的整条作废,不要人工救)

| # | 规则 | 为什么 |
|---|---|---|
| 1 | `answer` 在正文里能原样找到 | 幻觉护栏 |
| 2 | `required_context` 每一项都能原样找到 | 幻觉护栏 |
| 3 | `trap_answer` 能原样找到,且 ≠ `answer` | 幻觉护栏 |
| 4 | `required_context` 里没有任何一项是 `answer` 的子串,也不包含 `answer` | 否则判定退化成恒真 |
| 5 | `answer` 长度 ≥ 2 | 单字符会到处命中 |

再加一条**不作废、只打标记**:`answer` 在正文里出现 > 5 次 → 标 `needs_review`。出现太多通常说明选了一个过泛的串(比如选「5万」而不是「28000 - 68000」)。

### 6. 人工种子集(100~200 条)

**分三列各测一遍一致率,不要只测整体** —— 三列难度差得远:

| 列 | 预期一致率 | 不达标怎么办 |
|---|---|---|
| `answer` | > 90% | 改 prompt |
| **`required_context` 该不该填** | **最容易分歧,是全套评测的支点** | **< 80% 就别用 LLM 标这一列** |
| `trap_answer` | 中 | 依赖上一列 |

**推荐分工**:`answer` 交给 LLM(便宜且准),`required_context` 人工标(难且关键)。这样绕开了幻觉风险最大的一列,人工量也可控 —— 多数 query 这一列就是空。

## 第二部分 · 评测

对**每一条 gold × 每一套切分**算 4 个数。全部是纯字符串计算,不碰 embedding,几分钟跑完。

### 1. 完整命中(0 / 1)

> 存在一个 chunk,同时含 `answer` **和全部** `required_context`。

`required_context` 为空时自动退化成「有 chunk 含 answer 就算命中」。**同一条规则同时覆盖普通 query 和双胞胎 query。**

### 2. 陷阱(0 / 1)

> 存在一个 chunk,同时满足三条:
> **a.** 含 `trap_answer`
> **b.** **不含** `answer`
> **c.** `trap_answer` 在该 chunk 内**最近的标题**含 `required_context`

第 c 条的算法:

```
列出该 chunk 里出现的所有标题段落及其字符位置
对 trap_answer 的每一个出现位置:
    取字符距离最小的那个标题
    若该标题包含 required_context → 判为陷阱
```

**为什么需要第 c 条**:有个 chunk 含「历史类」(来自导语「本文整理了历史类和物理类的数据」)和物理类的 29273,按纯子串规则会被判成陷阱 —— 但 29273 最近的标题是「1、物理类」,**这个 chunk 其实正确标注了那些数字**。用「最近标题」而不是距离阈值,免调参。

**分母是 `trap_answer` 非空的 query 数,不是全部 query 数。**

### 3. 证据区间

> 正文里同时覆盖 `answer` 和全部 `required_context` 的**最短字符区间**。

`alt_evidence` 为 true 时正文有多处 —— 每处各算一个区间,后续指标取**最好的那一处**。

> 更准的做法:标注时直接输出 `evidence_span`(起止字符位置)。自动推导的最短窗口只是近似。

### 4. Precision_Ω 与证据碎片数

```
S = 与证据区间相交的 chunk 集合

Precision_Ω = 证据区间被 S 覆盖的字符数 ÷ S 中所有 chunk 的总字符数
证据碎片数   = |S|        (1 = 证据完好在一块内)
```

`Precision_Ω` 回答「为了拿到证据,得顺带背多少废话」,是唯一能量化「chunk 有没有变臃肿」的指标。来自 Chroma 技术报告,不需要检索即可计算。

### 5. 汇总表

| 方法 | 完整命中率 | 陷阱率 | Precision_Ω | 碎片数 | chunk 数 | 索引倍数 |
|---|---:|---:|---:|---:|---:|---:|
| A 定长贪心 | | | | | | 1.00× |
| B1 边界约束 | | | | | | |
| C 语义切分 | | | | | | |

### 6. 必须分层

**按 `required_context` 是否为空拆成两张表:**

| 子集 | 什么 query | 哪个指标有区分力 |
|---|---|---|
| `required_context` **非空** | 双胞胎 query | **陷阱率** |
| `required_context` **为空** | 普通 query | **完整命中率** |

实测依据(两篇真实文档):

| 文档 | A → B1 完整命中 | A → B1 陷阱率 | 谁在区分 |
|---|---|---|---|
| 高考一分一段表 | 2/4 → 4/4 | **50% → 0%** | 陷阱率 |
| 医美价格表 | **8/10 → 10/10** | 0% → 0%(全平) | 完整命中率 |

**两类文档的失败模式相反。只报总平均会互相抵消,得出「几种切法差不多」的错误结论。**

### 7. 置信区间

三套共享同一批 query,天然配对:

```
对 query_id 有放回重采样 2000 次
每次计算「B1 的指标均值 − A 的指标均值」
取 2000 个差值的 2.5% 与 97.5% 分位
```

**CI 跨过 0 = 没有统计显著差异。** 切分收益量级本来不大,常被 embedding 模型差异盖过,没有 CI 的结论不成立。

### 8. 怎么读结果

| 观察到 | 结论 |
|---|---|
| 非空子集:陷阱率显著↓ | ✅ 边界约束有效,核心论据 |
| 空子集:完整命中显著↑ | ✅ 标签与数据的分离被修好了 |
| 完整命中↑ 但 `Precision_Ω`↓ | chunk 变臃肿,调 `max_size` |
| 语义切分在两个子集上都赢不过边界约束 | 砍掉语义臂,也不必做「标题+语义」组合 |
| 全部差异都落在 CI 之内 | 切分不是当前瓶颈,去查 embedding 模型 |

---

## 三件不要做

1. **不要拿 `clicked_chunk` 当标准答案** —— 它由现有切分方法生成,会让基线天然占便宜。
2. **不要让 LLM 参与打分** —— 标注只做一次,之后所有方法用同一段程序计算。
3. **不要在标注之后改规范化正文** —— 所有字符位置会失效。规范化必须在标注前冻结。

---

## 局限

- 判定基于子串匹配,只适用于答案是干净短串的情况。**需要跨句合成的长答案要升级成字符区间标注**(`evidence_span`)。
- 「完整命中」是**能否召回的上界(oracle)**,不证明检索器真会把那个 chunk 排进 Top-K。要回答这个问题需要真检索评测。
- 一篇文里同一问题可能有多处合法证据(`alt_evidence`)。全量评测时需要 pooling 盲评,否则会把「召回了另一处合法证据」的方法误判为不相关。
